GitHub Universe 2026：「完成した作業」を出力にする、エージェント前提の開発基盤と、Git の作り直し

2026年10月28日の GitHub Universe の発表（Copilot アプリ、Fusion、projects、automations、コードレビュー Max、エンタープライズの契約）と、エージェントの増加に合わせた Git の保存の作り直し（5,000のエージェントが毎秒7,200プッシュ）、Octoverse 2026 の数字を、GitHub の公式ブログから整理する。

初回公開 2026-11-06 ／ 更新日 2026-11-06

ひとことで言うと

GitHub は10月28日の Universe で、GitHub を「アイデアから完成したソフトウェアまで」を届ける基盤と位置づけ、開発者が方向を決めて、エージェントが実装と検証をする形を打ち出した。出力として大事なのは、コードの量ではなく、機能、バグ修正、セキュリティ修正といった「完成した作業」だとしている。

新しい機能は、Copilot アプリ、モデルを自動で選ぶ Copilot Fusion、複数のリポジトリにまたがる Copilot projects、端末をまたいで続けられるセッション、結果から学ぶ automations、深く見るコードレビュー Max。あわせて、エンタープライズの契約者は別の契約なしに Copilot の機能を使える（使った AI クレジットの分を払う）ようになった。

土台では、今年の追加が CPU コア400万、ストレージ160 PB、ネットワーク50 Tb/s。Git の保存の仕組みも作り直していて、社内の試験で、5,000のエージェントが1つのリポジトリに毎秒7,200回プッシュできた。限定的な先行公開中で、広い展開は来年の初めとしている。

発表された製品と機能（10月28日、Jay Parikh 氏のブログ）

  • 考え方：ソフトウェア開発のライフサイクルは直線ではなくなり、コードの変更、同僚からの依頼、本番の指標のどれからでも作業が始まる。開発者は方向を決め、判断し、出すものに責任を持つ。エージェントは実装と検証をする。目指すのは、速度（アイデアから完成まで）、知能（プラットフォーム全体の文脈と、使うほどよくなる学習）、品質（既定で安全にし、出る前にバグを見つける）の3つ。
  • GitHub Copilot アプリ：エージェント前提で作ったアプリ。プロジェクトをまたいでエージェントとツールをつなぎ、イシューからマージまでを1つで扱う。コードを書くだけでなく、仕様書、設計の議論、テレメトリの分析もできる。
  • Copilot Fusion：推論、コード生成、デバッグ、ツールの使用という、作業に必要なことを評価して、1つ以上のモデルでの実行の仕方を選ぶ。GitHub は、Artificial Analysis の Coding Agent Index で、Fusion Max が Opus 5.5 Max に2ポイント以内で、半分のコストで、1タスクあたりの時間が40%少なかった、と書いている（GitHub による記述で、独立した確認ではない）。
  • Copilot projects：複数のリポジトリにまたがるエージェントの作業を、管理された並列のセッションで動かし、進み具合の確認と判断を1か所でする。Copilot アプリで、10月28日から使える。
  • セッションの継続：GitHub のアプリ、VS Code、CLI、Web のどれからでも、同じクラウドのエージェントのセッションを始め、追いかけられる。
  • Copilot automations：リポジトリの中で、クラウドで動く AI の作業の流れを作る。手動、イベント、スケジュールで動き、イシューの仕分けやコードレビューなどを調整する。新しく、結果から学んで、改善案を出し、人が確認して承認できる。
  • Copilot code review Max：GitHub は、重大度の高い問題の ReviewBench で、F1 スコアが最も高かったと書いている（GitHub による記述）。Lite と Balanced は日常のレビュー用で、Max は深く見るとき用。
  • 契約：10月28日から、GitHub Enterprise の顧客は、別の Copilot の契約なしに、Copilot アプリ、コードレビュー、automations などを使える。使った AI クレジットの分を払う。GitHub の営業経由で今日から、セルフサービスは近日。既存の Copilot Business・Enterprise の顧客は、現在のプランのままでも、移行してもよい。

インフラ（Universe の発表と、エンジニアリングのブログ）

  • 今年の追加：CPU コア400万、高速ストレージ160 PB、ネットワーク50 Tb/s。Azure でのマルチリージョン展開へ移行中で、完了は来年の初めの見込み。
  • 背景（エンジニアリングのブログ、10月6日）：エージェントと開発者が同じリポジトリで同時に動き、1日に数百万のコミットを受けるリポジトリがある。9月の1か月で73.8億コミット（前年の5倍超）。8月に最もにぎやかなリポジトリは、約10億回の要求を受けた。Git の活動の総量は、2025年9月から2026年8月で、月2,182億件から4,733億件に増えた（2倍超）。
  • 課題として挙がったもの：エージェントは、ほぼ1動作ごとにコミットするため、1回のプッシュの遅さが上限になる。書き込みの量が桁違いに増える（プッシュは月6.9億回から33.5億回）。マージが1つの参照に集中する（マージの量は前年の約4倍）。1回のプッシュが、CI やコードスキャンの数千の読み取りに広がる（GitHub Actions は9月に32.6億回で、前年の4倍超）。リポジトリのデータを整理する作業が積み重なる。
  • 今の仕組みの限界：各リポジトリを、Spokes が、複数のファイルサーバー（既定は5台）のローカルディスクに全コピーで持つ。コピーが「正」であり、読み取りの余力を増やすには、耐久性のあるコピーを増やすことになる。すべてのコピーが書き込みに加わるので、読み取りを増やすと、書き込みが遅くなる。リポジトリが非常ににぎやかだと、これが上限になる。
  • 作り直しの原則（3つ）：調整を最小にする（合意が要るのは参照の更新だけで、オブジェクトの保存や検証などは並行できる）、保存と計算を切り離す、調整は必要なところだけ。整理（圧縮・ごみ集め）の作業は、実際に要求に答えるホストから外す。
  • 新しい保存の仕組み（11月5日のブログ、コードネーム「Rubicon」）：Git のオブジェクト（パック）は Azure Blob Storage に置く。参照とパックの一覧は、別に複製された記録のサービス（Ref-CAS）に置く。要求は、使い捨ての計算（仮想レプリカ）が処理し、ローカルのディスクは作り直せるキャッシュ。にぎやかなリポジトリには仮想レプリカを足す。整理は、専用の圧縮ノードが Blob Storage に対して背景で行う。書き込みは、仮想レプリカがパックを索引して Blob Storage に上げ、Ref-CAS に1回の取引で、パックの登録と参照の更新を書く。
  • 試験の結果：社内の試験で、1つのリポジトリに、5,000のエージェントが毎秒7,200回のプッシュを送り、読み取りの遅延は低いままだった。限定的な先行公開（プライベートプレビュー）で、広い展開は来年の初め。
  • 次の計画（ブログ）：必要なオブジェクトだけ読む、種類ごとにパックを整理する、部分的なレプリカ、すぐ使える形の保存、どのリージョンにも置けるレプリカ、使われていないときは縮める。エージェントの操作を安くする（クローンなしの作業、複数ファイルを1回で確定するコミットの API、イベントの配信）。Git 自体の改善（軽いクローン、隠れた計算量の増加の除去、履歴を速くたどる、よくある失敗の警告）。

Octoverse 2026（10月28日）の数字

  • 過去12か月のプッシュは179億回。2024年と2025年の合計より多い。すべての種類のリポジトリ（公開と非公開）のコミットは343億回で、2年前の3倍超。マージされたプルリクエストは13億件で、1日平均350万件。
  • エージェントの設定ファイルがあるリポジトリは、今年作られたものの中で、ないものより、平均して8倍のコミットがあった。9月時点で、プルリクエストの40%超をエージェントで始める（3月は17%）。
  • 複数のモデルを使った Copilot の利用者は9月に61%。
  • GitHub Actions は、今年、1秒に1,440回のジョブを動かした（1日に1.24億回）。Dependabot のプルリクエストは3,000万件超がマージされ、2025年の約2倍のペース。
  • 公開リポジトリへの貢献は25億回で、前年（11.2億回）の2倍超。
  • 開発者は2.25億人超。米国が3,830万人、インドが3,200万人（それぞれ、今年1,000万人以上増えた）、中国1,240万人、ブラジル1,020万人、日本715万人。ブラジルは今年328万人増えて、国別で3番目。
  • 今年初めて、業種別の公開リポジトリの見方を示した。鉱業、建設、医療、農業のリポジトリは、2022年から、それぞれ数倍に増えた。

読むときの注意

  • いずれも GitHub の公式の記述で、第三者の確認ではない。モデルの比較（Fusion）やレビューの評価（Max）は、GitHub が示した指標と数字。
  • 機能の使える範囲やプランは、一部が「今日から」「近日」「プレビュー」で、組織や契約によって違う。
  • Publickey が伝えた「180倍」と「Copilot Dreaming」は、読んだ原本で確認できなかったため、扱っていない。
  • 新しい Git の保存の仕組みは、限定的な先行公開で、広い展開は来年の初め。試験の数字は社内の試験。

見方（筆者の整理）

  • 発表の中心は、「コードを速く書く」から、「完成した作業を出す」に変わっている点。複数のリポジトリ、端末をまたぐ継続、結果からの学習、レビューの強化は、いずれもエージェントが長く動き、並列で動くことを前提にしている。
  • 同じ公式の資料が、エージェントによる活動の増加（プッシュ4.9倍、コミット5倍超）を数字で示したうえで、それに耐える Git の作り直しを説明している。製品の発表と基盤の投資が、同じ問題（エージェントの量）に向いている。
  • Git の読み取りを増やすと書き込みが遅くなる、という構造は、エージェントが多数の書き込みをするようになったことで、はじめて上限になった。ブログは、にぎやかなリポジトリのための設計が、すべてのリポジトリに効くと書いている（GitHub の主張）。
  • 契約の変更（別の契約なしで使い、使った分を払う）は、席の数ではなく、AI の使用量で課金する方向を示している。
