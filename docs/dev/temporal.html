Temporal：失敗しても続きから再開する、耐久実行のワークフロー実行基盤

Temporal について、一言での説明、中身と仕組み（構成、形、成り立ち、動き方、目的）、AWS Step Functions や Apache Airflow との違い、使う前の条件と使った結果、代表例と使いどころ、限界と注意を、公式の文書から整理する。

初回公開 2026-11-26 ／ 更新日 2026-11-26

一言で言うと

Temporal は、ワークフロー実行基盤の一種で、アプリのコードの実行を、履歴に記録し、失敗のあとに、続きから再開させる点（耐久実行）が違います。

中身と仕組み

調査メモの項目（構成要素、外から見た形、成り立ち、仕組み、使う目的）の順に、公式の文書で確認したことを書きます。

何でできているか

  • Temporal Service：Temporal Server（Go で書かれている）と、データベースからなります。公式の用語では、以前の Temporal Cluster を、いまは Temporal Service と呼びます。
  • Temporal Server の内部サービス：Frontend、History、Matching、Internal Workers。History が Workflow Execution を管理して状態を保存し、Matching が、Worker がポーリングする Task Queue を管理します。
  • データベース：実行の状態と履歴を保存する永続化ストアと、実行の一覧や検索のための可視性（Visibility）ストア。
  • Worker Process：利用者が運用し、SDK を使って、Workflow と Activity のコードを動かします。

どんな形か

  • 利用者のアプリは、SDK を gRPC のクライアントとして使い、Workflow の開始、取り消し、操作をします。
  • 操作の窓口は、SDK、Web UI、CLI（temporal コマンド）です。動いている Workflow には、Signal、Update、Query を送れます。
  • Workflow と Activity は、汎用言語のコードで書きます。SDK は8つ（Go、Java、.NET、PHP、Python、Ruby、Rust、TypeScript）あり、言語の違う Workflow どうしが、互いに呼び出せます。
  • 公式の開発ガイドの表示（2026年11月25日に取得）は、Go v1.51.0、Java v1.41.1、.NET v1.22.0、PHP v2.20、Python v1.36.1、Ruby v1.11.0、Rust v1.3.0、TypeScript v1.26.0 です。

どう作られたか

  • Uber の Cadence から分かれて作られました。開発元の Temporal Technologies は、Cadence の作者たちのスタートアップです。会社の紹介によれば、創業者の2人は、2015年に Uber で Cadence を共同で作りました。ライセンスに、Uber Technologies（2020年）の著作権表示が残ります。
  • 提供元は Temporal Technologies Inc. で、サーバーは MIT ライセンスです。SDK は、Java が Apache License 2.0、Go、TypeScript、Python、.NET、Ruby、PHP、コアが MIT です。
  • 提供の形は2つあります。利用者がサーバーとデータベースを運用する形と、提供元が運用するクラウド版（Temporal Cloud）です。クラウド版は従量課金で、Actions と Storage の消費と、サポートプランの組み合わせです。

どう動くか

  • イベントソーシング：Workflow Execution ごとに、イベントの履歴（Event History）を追記します。
  • 失敗のあと：Workflow のコードを最初から実行し、履歴を使って、以前の状態に戻します（リプレイ）。履歴に記録済みの結果を使うので、記録済みの Activity は再実行しません。
  • 決定的であること：リプレイのため、Workflow のコードは、同じ履歴で、同じ判断をする必要があります。時刻、乱数、ネットワーク呼び出しなど、実行のたびに変わりうるものは、Workflow のコードに直接書かず、SDK の機能や Activity で扱います。
  • Worker の動き：Task Queue をポーリングして、Workflow Task と Activity Task を受け取ります。Workflow Task は、コードが止まるところまで進め、続きの指示（コマンド）をサービスに返します。Activity Task は、Activity を実行して、結果を返します。
  • 再試行：Activity が失敗すると、再試行の方針（Retry Policy）に従って、自動で再試行されます。再試行に備えて、Activity のコードは、冪等にすることが勧められています。

何のためか

  • 公式は、再試行のループ、状態の表、スケジューラ、人の承認を待つ受け口、取り消しの処理、バックグラウンドジョブ、AI エージェントの長い処理を、アプリのコードから基盤に移すことを、目的に挙げます。
  • 数秒から数か月（Workflows のページは、数年）にわたる処理を、クラッシュやネットワーク断があっても、完了まで実行することを狙います。

使う前の条件と、使った結果

使う前の条件

  • データベース：永続化のデータベースが必須です。テストされているのは、Cassandra（v3.11、v4.0、5.0.4 以降）、PostgreSQL（13.18、14.15、15.10、16.6）、MySQL（v5.7、v8.0。8.0.19 以降）です。SQLite は、開発とテストだけです。
  • 可視性ストア：本番では、Elasticsearch が推奨されます。1.20 以降は、MySQL 8.0.17 以降、PostgreSQL 12 以降、SQLite 3.31.0 以降でも、高度な可視性が使えます。
  • Worker：利用者が自分で運用します。SDK で、Workflow と Activity のコードを書きます。
  • 互換と移行：サーバーのアップグレードは、minor の版を1つずつ上げます。スキーマの更新のあと、バイナリをローリングで更新し、実行中の Workflow は動き続けます。Worker Versioning は、実行中の Workflow を、開始したときの Worker の版に固定します。

使った結果

  • Workflow Execution は、完了まで実行され、履歴が残ります。
  • Web UI で、入力、出力、履歴（どの Activity が、どのエラーで失敗したか）を見られます。CLI で、開始、確認、取り消し、終了ができます。
  • Search Attributes で、業務のデータを条件に、実行を検索できます。
  • 通信は mTLS で保護できますが、既定では、履歴のデータは、サービス側で保存時に読めます。Data Converter で、データを暗号化できます。

具体例と、使いどころ・限界

代表例

  • 公式の例：注文処理の Workflow です。公式は、Workflow Type の例として、order processing と customer onboarding を挙げます。Activity の例は、他のサービスの呼び出し、メディアの変換、メールの送信、ユーザー情報の更新、クレジットカードの支払いです。
  • 最小の動かし方：brew install temporal のあと、temporal server start-dev で、開発用のサーバーを起動し、Go または Java のサンプルを動かします。

使いどころ

公式の説明から、筆者がまとめたものです。

  • 長く、複数の段階があり、途中で失敗しうる処理（支払い、注文の処理など）。
  • 人の承認や、数日の待ちを含む処理。
  • 失敗したときに、前の段階を取り消す補償の処理（Saga パターン）。
  • バックグラウンドジョブ（Standalone Activity を、ジョブのキューとして使う）。
  • AI エージェントの、長く、失敗しやすい呼び出しの連続。

限界と注意

  • Workflow のコードは、決定的であること。時刻、乱数、ネットワーク呼び出しを、直接書かない。
  • 自前運用の既定の制限：ペイロードは 2 MB でエラー（512 KB で警告）、gRPC のメッセージは 4 MB、1つの Workflow の履歴は 50 MB または 51,200 イベントでエラー、同時に未完了の Activity などは 2,000（性能のためには 500 以下を推奨）。
  • 提供元の記述：1つの Worker は、更新の頻度を扱える限り、数百万の未完了の Workflow Execution を扱えます。遅延は少し増えます。
  • データの保護：既定では、履歴のデータが、サービス側で保存時に読めます。Data Converter で暗号化します。通信は mTLS、認可はプラグインで設定できます。
  • 運用：自前で運用すると、データベース、可視性ストア、各サービスの運用が要ります。クラウド版は、それを提供元が運用します。
  • 最新のサーバーは v1.32.2（2026年11月2日公開）です。リリースノートに、脆弱性の修正が含まれると書かれています（内容は未確認）。

用語メモ

耐久実行（Durable Execution）
実行の状態と進み具合を保存し、失敗のあとに、続きから再開する仕組み。
Workflow
一連の処理の流れ。コードで書く。Workflow Definition が定義、Workflow Execution が、実行中の1件。
Activity
外の世界に触れる、1つの処理（API の呼び出し、データベースの問い合わせなど）。失敗すると、再試行される。
Worker
Workflow と Activity のコードを動かす、利用者が運用するプロセス。
Task Queue
Worker が、仕事を受け取るための待ち行列。
Event History
Workflow Execution で起きたことの、追記だけの記録。
リプレイ
履歴を使って、コードを最初から再実行し、以前の状態に戻すこと。
決定的
同じ履歴を与えれば、同じ判断をすること。
冪等
同じ処理を何度行っても、結果が変わらないこと。
mTLS
クライアントとサーバーが、互いに証明書で確認し合う、暗号化された通信。
Data Converter
データの変換（暗号化など）を、SDK の側で行う仕組み。
Cadence
Uber が作った、ワークフローのエンジン。Temporal の元。
