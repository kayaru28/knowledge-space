Node.js：ブラウザの外で JavaScript を動かす、イベントループと非同期 I/O の実行環境

Node.js について、一言での説明、3行の要約、Deno や Bun との違い、前後で組み合わされる仕組み（V8、libuv、npm）、具体的な仕組み（イベントループ、スレッドプール、版の周期、使いどころ、限界と注意）を、公式の文書から整理する。

初回公開 2026-11-17 ／ 更新日 2026-11-17

一言で言うと

Node.js は、ブラウザの外で JavaScript を動かすための、オープンソースでクロスプラットフォームの実行環境で、1つのイベントループと非同期の入出力で、多数の接続を少ないスレッドでさばくことを設計の中心にしています。

3行で表すと

  • 何であるか：Google の JavaScript エンジン V8 を、ブラウザの外で動かし、非同期の入出力の部品を標準で備えた実行環境。MIT ライセンスで、OpenJS Foundation が支援する、オープンなガバナンスのプロジェクト。
  • 何ができるか：ネットワークのアプリケーション（HTTP はストリーミングと低遅延を意識した「第一級」の機能）を、リクエストごとにスレッドを作らず、1つのプロセスで動かせる。標準で、テストの実行、TypeScript の型の除去、権限の制限、ワーカースレッドなども備える。
  • 何が特徴か：イベントループを、ライブラリではなく、実行環境の組み込みの仕組みとして持つ。待つ処理（入出力）は非同期で、ブロックする処理は例外とする設計。2027年の第27版から、年に1回の新しい版が出て、すべての版が長期サポート（LTS）になる。

前後で組み合わされるもの

縦のつながりです。前段と後段の分け方は、筆者の整理です。

前段：Node.js が動くための土台

  • V8：JavaScript と WebAssembly を実行するエンジン。Node.js は、これをブラウザの外で動かす。
  • libuv：Node.js のために書かれた、クロスプラットフォームの支援ライブラリ。イベントループと、非同期の入出力、スレッドの機能を提供する。Node.js のイベントループと、プラットフォームの非同期の動作のすべてを実装するものだと、公式の指針が説明する。
  • OS の入出力の仕組み：ネットワークの入出力は、ノンブロッキングのソケットを、Linux なら epoll、macOS などの BSD なら kqueue、SunOS ならイベントポート、Windows なら IOCP で待つ。
  • ネイティブアドオン：C や C++ で書いた拡張は、Node-API を通じて作る。Node-API は、JavaScript エンジン（V8 など）から独立で、Node.js 本体の一部として保たれ、版をまたいで ABI が安定する。そのため、ある主要な版でビルドしたものが、あとの主要な版でも動く。

後段：Node.js を使う上位の仕組み

  • npm：公式の説明では、ウェブサイト、コマンドラインの道具、レジストリの3つからなる。JavaScript のパッケージを共有し、取得するための、世界最大のソフトウェアのレジストリだと書く。
  • アプリケーションとサービス：ネットワークのサーバー、ツール、スクリプトなど。複数の CPU のコアは、child_process.fork()、cluster モジュール、ワーカースレッド（node:worker_threads）で使う。
  • 配布の形：単一の実行ファイル（SEA）の機能で、Node.js が入っていない環境にも、アプリを配れる。この機能は、実験的（安定度 1.1：開発が活発）。
  • TypeScript：型を取り除いて実行できるが、型の検査はしない。tsconfig.json を使う完全な対応には、tsx のような外部のパッケージが要る、と公式の文書が書く。
  • ライブラリの作者の検証：Node.js の側は、主要なパッケージのテストを、次の版で走らせて、エコシステムへの影響を事前に見つける仕組み（CITGM）を持つ。

具体的な仕組み

なぜ必要か

  • 公式の説明では、Node.js は、スケールするネットワークアプリケーションを作るために設計された。1つのプロセスで、リクエストごとに新しいスレッドを作らずに動き、スレッドの同時実行の管理の負担なしに、1台のサーバーで数千の同時接続を扱える、と書く。
  • そのために、標準ライブラリが、非同期の入出力の部品を備え、ブロックする動作は、通常ではなく例外にする、と説明する。
  • 公式の発表は、Node.js は主にボランティアが保守していて、複数の版を同時に支えるのは負担が大きい、とも書く。これは、版の仕組みの背景の説明（下の「版の周期」）。

どう動くか

まず、イベントループです。

  • 入力のスクリプトを実行したあと、Node.js はイベントループに入り、実行すべきコールバックがなくなると、ループを抜ける。
  • ループの1周は、段階を順にたどる。公式の解説の順は、timers（setTimeout() と setInterval() のコールバック）、pending callbacks（次のループに回された入出力のコールバック）、idle と prepare（内部だけで使う）、poll（新しい入出力の事象を取り、入出力のコールバックを実行する。必要なときはここで待つ）、check（setImmediate() のコールバック）、close callbacks（ソケットの close など）。
  • process.nextTick() は、技術的にはイベントループの一部ではなく、いまの操作が終わったあとに、どの段階にいても処理される、と解説が書く。
  • libuv 1.45.0（Node.js 20）から、タイマーは、各周回の poll の段階のあとに実行される、と解説が書く。

次に、入出力が、どこで動くかです。

  • ネットワークの入出力は、ループのスレッドだけで行う。待つ仕組みは、OS ごとに最適なもの（epoll、kqueue、イベントポート、IOCP）を使い、実行モデルは、Unix と Windows で揃えられている（libuv の設計文書）。
  • ファイルの入出力には、プラットフォームに共通の非同期の仕組みがないため、libuv は、ブロックする入出力を、スレッドプールで実行する。スレッドプールで動くのは、ファイルシステムの操作、DNS の関数（getaddrinfo と getnameinfo）、uv_queue_work() で指定した利用者のコード。
  • スレッドプールは大域で、全部のループが共有する。既定の大きさは4で、起動時に環境変数 UV_THREADPOOL_SIZE で変えられる（上限は1024）。公式の指針は、Node.js では、DNS の dns.lookup()、fs の API（一部を除く）、暗号の pbkdf2() や scrypt() など、zlib の API（同期のものを除く）が、このワーカープールで動くと書く。

最後に、版の周期です。

  • 第26版までは、半年ごとに新しい主要な版が出て、偶数の版だけが LTS になった。
  • 第27版から、年に1回（4月）に新しい主要な版を出し、すべての版が LTS になる。各版は、10月に Alpha を始めて6か月（3月まで）、4月に Current になって6か月、10月から LTS になり30か月で、合計36か月で終了する。第27版から、LTS の版は、Maintenance の段階を経ない。
  • 2026年11月17日の時点：v22（Jod）と v24（Krypton）は Maintenance LTS、v26（Lithium）は Active LTS（2026年10月28日から）、v27 は Alpha（2026年10月28日から）。v20 は2026年4月30日に、v25 は2026年6月1日に終了した。日程は変わりうる、と書く。

近年の機能と、公式の安定度の区分です（API 文書 v26.13.1）。

  • 安定度は、0（非推奨）、1（実験的。1.0 開発初期、1.1 開発が活発、1.2 リリース候補）、2（安定）、3（レガシー）の区分。実験的は、セマンティックバージョニングの対象外で、本番での使用は勧めない。
  • 安定（2）：テストの実行（node:test、node --test。v20.0.0 から安定）、権限モデル（v20.0.0 で追加、v23.5.0 と v22.13.0 から実験的ではない）、TypeScript の型の除去（v22.6.0 で追加、v23.6.0 と v22.18.0 で既定で有効、v25.2.0 と v24.12.0 で安定）、ES モジュール、ワーカースレッド（v12.11.0 から実験的ではない）。
  • 実験的：単一の実行ファイルのアプリ（安定度 1.1。v19.7.0 で追加）。

使いどころ

  • 多数の同時接続を扱う、ネットワークのサーバー（公式が掲げる設計の目的）。HTTP は、ストリーミングと低遅延を意識して設計されている。
  • 入出力が中心の処理。待つ時間が多く、計算の時間が短い処理に向く（イベントループの設計から、筆者の整理）。
  • 配布の面では、Node.js が入っていない環境に、アプリを単一の実行ファイルで配る（実験的）。
  • ライブラリの作者は、Alpha の版を CI に早く取り込むよう、公式の発表が勧める。LTS だけで試すと、利用者に影響が出る前に不具合を報告できない、と書く。

限界と注意

  • ブロックする処理に弱い：JavaScript のコールバックが長くかかると、それを動かしているスレッドが止まる。公式の指針は、各コールバックを速く終えるよう求める。
  • 同期の API：サーバーでは使わないよう挙げているもの：crypto.randomBytes（同期）、crypto.pbkdf2Sync、zlib.inflateSync、fs の同期の API、child_process.spawnSync など。
  • 大きな入力の JSON：50MB の文字列で、文字列化に0.7秒、解析に1.3秒かかる、と指針が例を挙げる。
  • 正規表現（ReDoS）：入れ子の量指定（例：(a+)*）などで、イベントループが実質止まりうる。入力の長さを制限して拒否することも勧める。
  • 対策：作業を小さく分けて、ときどきほかの事象に譲る（例：setImmediate() で次の段階をつなぐ）。重い処理は、ワーカープールやワーカースレッドなどに出し、イベントループは、要求をさばく司令塔にとどめる。クライアントごとに子プロセスを作ってはいけない、と指針が警告する。
  • スレッドプールは小さい：既定で4で、ファイル、DNS、暗号、圧縮の処理が、同じプールを分け合う。
  • 権限モデルは「シートベルト」：信頼できるコードの誤りを防ぐもので、悪意のあるコードへの保証はない、と公式の文書が書く。
  • TypeScript は型の検査をしない：型を取り除くだけ。tsconfig.json を使うには、外部のパッケージが要る。
  • require() での ES モジュールの読み込み：同期の ES モジュール（トップレベルの await を使わないもの）だけに対応、と文書が書く。
  • Alpha と Current の版は、本番の使用向けではない：公式の README が、ライブラリの作者や CI 向けと書く。
  • 日程は変わりうる：版の日程は、公式が「変更されうる」と書く。
