AIコーディングで生産性は上がったか：2本の研究から見える「増えた量」と「追いつかないレビュー」

Microsoft の数万人を追った研究と、802人の開発者を追った研究の、2本の論文（arXiv）をもとに、AIコーディングツールの導入で何がどれだけ増え、何が追いつかなくなったのか、どこまで言えるのかを図で整理する。

初回公開 2026-10-19 ／ 更新日 2026-10-21

ひとことで言うと

AIコーディングツールを導入した開発者は、マージされるプルリクエスト（PR）の数が増えました。Microsoft の研究では約24%、802人の開発者を追ったもう1つの研究では、1人あたり2.09倍（保守的な推定では1.46倍）です。

ただし、どちらも測ったのは「PRの数」で、価値や品質そのものではありません。さらに後者の研究では、提出量が増えたぶん、レビューが追いつかなくなっていました。1人あたりのレビュー負荷は約2倍になり、人間のレビューは薄くなっています。

生産性はどれだけ上がったか

導入した人のマージPR数は、どちらの研究でも増えています。次の図は、それぞれの研究が示した増加率を並べたものです。基準や期間が違うため、棒の長さを直接比べることはできません。

論文1のそのほかの結果

  • 効果は約4か月のあいだ、続いていました。2月は+29.4%、3月〜4月は+20.0%で、信用区間は大きく重なっており、減衰は統計的に確認されませんでした。
  • 利用頻度が高いほど、増加も大きくなっていました（同一人物内の比較。因果ではなく関連）。週3日の利用で約+15.0%、週5日以上で約+50.1%です。
  • 単一のツールだけを使った人では、Claude Code の利用週は約+11.4%、Copilot CLI は約+24.9%でした。作業内容の違いなどの交絡の可能性があります。

論文2のそのほかの結果

  • 企業全体のPR数は、ベースラインの3.1倍でした。
  • 2022年以降のリポジトリでは+44%、それ以前のレガシーなリポジトリでは+12%（有意でない）と、コードベースによって効果が違いました。
  • 職位による有意な差はありませんでした。モデルのリリースごとの効果は、同時期の組織全体の利用の急増と切り分けられませんでした。

レビューが追いつかない

論文2の題名は、「AIは人間がレビューできるより速く書く」という意味です。提出量が増えると、レビューする側の負荷が増えます。

レビューの中身も変わっていました。次の図は、PRのうち、各種のレビューを受けたものの割合の変化です。

品質の指標は

  • PR単位では、AIが生成したPRのマージ率は、人間のPRとほぼ同じで、リバート（取り消し）率は低めでした。
  • ただし、これらは粗く短期的な指標で、欠陥、インシデント、保守性を捉えていません。
  • AIが生成したPRは、最初の人間のレビューからマージまでの時間が約20%長く、総サイクル時間は約22%長くなっていました。

広がり方

論文1は、ツールを最初に使うきっかけを調べています。最も強く効いていたのは、周囲の人が使っていることでした。

  • 継続して使うかどうかは、事前のPR活動量が多い人（週2件以上）や、直属のマネージャーが使っている人で高くなりました。
  • IDE 版 Copilot を以前から使っていた人は、初めて使うオッズは上がる一方、継続利用のオッズは約12〜15%低くなりました。

どこまで言えるか

どちらの論文も、自分の限界を明記しています。

論文1（Microsoft）

  • 採用の分析は横断的で、同僚の影響と同類性を切り分けられない
  • 導入者は自ら選んでいるため、選択バイアスがありうる
  • マージPR数は、品質、複雑性、コストを捉えない。論文自身が「マージPRは価値そのものではない」と明記
  • 単一企業、単一期間。16週間では長期的な低下は評価できない
  • 著者は Microsoft の社員で、同社はAIツールを販売し GitHub を所有している

論文2（802人の企業）

  • 導入時期と利用量は開発者自身が選んでおり、ランダムに割り当てられていない。因果は厳密には特定されておらず、「強く示唆する」証拠として読む
  • 若くAIに積極的な企業で、ツール予算に上限がない好条件。外的妥当性は限定的
  • PR数は活動量のみ。マージ率とリバート率は粗く短期的
  • 論文は、約2倍の増加を「好条件では達成可能だが、即時でも典型的でも無償でもない」と位置づけている

関連する調査：State of Devs 2026

10月21日の追記です。Devographics の開発者調査「State of Devs 2026」（2026年7月5日〜9月5日、回答者5,463人）の結果ページに基づきます。2本の論文とは違い、開発者本人が答えた割合で、生産性や品質を測ったものではありません。

筆者の整理：「コードの多くをAIに書かせている」と答える開発者が約半数います。論文2が示した「提出量が増え、レビューが追いつかない」状況が、広く起きうることを示す材料になります。ただし、回答者は調査に答えた人に限られ、割合は本人の感覚で、国や職種の偏りもありえます。AIへの感情は、肯定的が49%、否定的が42%でした。

実務に生かすなら

論文の内容を並べて読んだ上での、筆者の整理です。論文がそう述べているわけではありません。

  • PR数だけでなく、レビューの負荷（1人あたりの件数、コメントのあるレビューの割合）も一緒に測る。
  • 提出量が増えるなら、レビューの体制（人数、自動化の範囲、承認の基準）も合わせて設計する。
  • 広げるときは、周囲で目に見える形で使われることが効く（論文1の提言）。
  • 他社の数字をそのまま目標にしない。測っているもの（PRの数）と、条件（好条件の企業、Microsoft）が違う。

用語メモ

プルリクエスト（PR）

マージ
PRの変更を、本流に取り込むこと。
リバート
取り込んだ変更を、取り消して元に戻すこと。
合成コントロール

差の差分法
導入した人と導入しない人の、導入前後の変化の差を比べる方法。
オッズ
ある事象が起きる確率を、起きない確率で割った値。オッズの上昇は、確率の上昇そのものではない。
信用区間
