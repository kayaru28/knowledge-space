一般知識

プロパティベーステスト：入力の例ではなく「常に成り立つ性質」を書き、入力はツールに大量に作らせて確かめる手法

プロパティベーステストについて、一言での説明、3行の要約、例ベースのテストやファジング、ツールとの違い、前後で組み合わされる仕組み、具体的な仕組み（なぜ必要か、使いどころ、限界と注意）を、各ツールの公式文書と2つの論文から整理する。

初回公開 2026-11-08 ／ 更新日 2026-11-08

一言で言うと

プロパティベーステストは、「この入力ならこの出力」という例を並べる代わりに、「どんな入力でも成り立つはずの性質」を書き、入力はツールが自動で大量に作って確かめ、失敗したら反例を示す手法である。

3行で表すと

  • 何であるか：入力と出力の関係について、すべての入力で成り立つはずの主張（性質）を、実行できる形で書く。ツールが入力を自動で作り（既定は100件前後）、性質が成り立つかを確かめる。
  • 何ができるか：人が思いつかなかった入力でも欠陥を見つけ、見つけたら反例（性質を破った入力）を示す。現行の主要なツールは、反例を小さく縮め、失敗を再現できるようにする。性質は、仕様の説明にもなる。
  • 何が特徴か：例を並べるテストを置き換えず、補う。代わりに、性質を考えること、入力の生成器を書くこと、テストの効き目を確かめることが難しい、と実務の聞き取りは報告する。

類似するものと、違い

横のつながりです。同じ目的の手法である例ベースのテストと、よく比べられるファジング、代表的なツールの違いを扱います。比較の軸は、筆者の整理です。

ファジングとの違い

  • fast-check の文書は、ファジングを「プロパティベーステストの一部とみなせる」と説明する。ファジングは、テストを繰り返し動かし、コードが落ちないことを確かめるもので、どちらもプロパティベーステストでできる、という理由。これは fast-check 自身の見方。
  • 聞き取り調査（Jane Street）は、使われ方の違いを観察した。プロパティベーステストは、部品の単位のテストとして、編集のたびに手元で動かす速いテストで、時間の予算は30秒から50ミリ秒ほどだった。ファジング（AFL など）は、アプリ全体の結合テストに使い、通常のテストの流れとは別に、数時間から数日走らせた。30人中10人がファジングに触れ、3人はプロパティベーステストと併用していた。1つの企業での観察。
  • Hypothesis の入門は、正しい形の入力でコードを呼ぶだけでも、落ちる欠陥が見つかることがある、と書く。入口が1つで、中のコードが多いプロジェクトで価値がある、という説明。

前後で組み合わされるもの

縦のつながりです。前段と後段の分け方は、筆者の整理です。

前段：プロパティベーステストが動くための土台

  • 性質を見つける：Hypothesis の入門は、見つけにくいときの手がかりを挙げる。往復の性質（符号化して復号すると元に戻る、など）、既存のテストの parametrize の置き換え、正しい形の入力で呼んでみること。他の例として、最適化版と、遅いが確実な版の一致、取引が常に釣り合うこと、コンパイラや整形ツールが正しい構文で落ちないこと、が挙がる。
  • 合否の基準（オラクル）：原典の論文は、合否を決める基準が要ると書く。簡単で、明らかに正しい版との比較も、性質として書ける。
  • 入力の生成器：型から導き出せる場合は、導出された生成器が好まれた（聞き取り調査）。前提のある入力（たとえば、整列済みの一覧）は、専用の生成器を書くのが最良、と原典の論文は書く。
  • 既存のテストの枠組み：Hypothesis は pytest が拾える。fast-check は、主要な JavaScript と TypeScript のテストの枠組みの中で動く。
  • 前提による絞り込み：条件に合わない入力は、捨てて作り直す。fast-check の文書は、厳しすぎる絞り込みは無駄が多く、可能なら生成器の設定（最小の長さなど）で指定するよう勧める。

後段：結果を使う仕組み

  • 反例の報告と縮小：失敗した入力を、小さくして示す。聞き取り調査では、縮小は「必要」と答えた人や、自作の枠組みに必ず入れた人がいた。
  • 失敗の再現と回帰テスト化：Hypothesis は、失敗を保存して次回に再生し、@example で入力を固定できる。ただし、Hypothesis の文書は、データベースは版や関数の変更で無効になりうるので、正しさのためには @example を使うよう勧める。聞き取り調査では、大きな反例を、別の回帰テストに引き出して調べる人がいた。
  • 通常のテストの流れ：聞き取り調査では、性質があることがコードレビューで正しさの強い手がかりになった。実行は速くなければならず、時間の予算を設けていた。
  • テストの効き目の確認：聞き取り調査で挙がった方法は、ミューテーションテスト（30人中7人）、生成された入力の目視（8人）、コードカバレッジ（2人）、性質自体のカバレッジ（1人）。ミューテーションテストは、別のまとめで扱っている。

具体的な仕組み

なぜ必要か

  • 例ベースのテストは、欠陥が潜む入力を、テストを書く人が思いつく必要がある。fast-check の文書は、経験のある開発者でも端を見落とす、と書く。
  • 性質は、入力を決めずに挙動を述べる。ツールが入力を作るので、思いつかなかった入力でも検査される。
  • 性質は、仕様の説明にもなる。fast-check の文書は、整列の性質（要素が同じ、昇順）を例に挙げる。聞き取り調査でも、30人中12人が、性質を文書として扱っていた。
  • 原典の論文は、純粋な関数は、状態を気にせずに細かい単位で検査しやすいと書き、性質を関数として書いて、多数のランダムな入力で自動で検査する道具を作った。実装は、約300行の1つのモジュールだった。

どう動くか

  • 流れ：（1）性質を、入力を引数に取る関数として書く。（2）生成器で入力を作る。（3）既定で100件前後の入力で、性質を動かす。（4）例外が出る、または偽が返れば失敗。（5）失敗した入力を縮める。（6）反例を示す。
  • 例（Hypothesis の入門）：選択ソートに対して、「整数の一覧」で検査すると通った。整数と小数の一覧にすると、[1.0, nan, 0] などの反例が見つかった。nan があると整列が決まらないため、生成から nan を除くことにした。性質を書く中で、仕様の曖昧さが見える例。
  • 入力の作り方：入力の大きさを変える（短いものと長いもの、小さい数と大きい数）。fast-check の文書は、0、1、-1 の近く、重複のある配列、__proto__ のような危険な文字列も含めて、欠陥が出やすい入力を狙うと書く。
  • 分布の重要性：原典の論文は、入力の分布を考えずにランダムテストを語るのは無意味だと書き、分布を人が制御できる生成器を設計の中心に置いた。
  • 縮小：失敗した入力から、要素を減らすなどして、同じ失敗が続く最小のものを探す。fast-check の文書は、数十要素の配列の失敗が、2から3要素で示されうると書く。
  • 再現：fast-check は、種を固定すれば、毎回同じ入力になる。固定しなくても、失敗時に種が示される。Hypothesis は、失敗した入力を保存して、次回は先にそれを試す。
  • 状態を持つテスト（Hypothesis）：入力だけでなく、動作の列を生成する。動作（ルール）を定義し、ツールが組み合わせて、失敗する列を探す。文書の例は、本物のデータベースと、辞書で作った単純な模型に同じ動作を行い、結果が食い違わないかを調べる。失敗したときは、短いプログラムの形で表示される。
  • 原典の時点：2000年の論文は、反例の縮小に触れていない（語の検索で確認した範囲）。現行の公式文書には縮小がある。

使いどころ

  • 性質を言いやすい部分：往復、遅いが確実な版との一致、不変条件。
  • 複雑な部品の信頼を上げる：聞き取り調査では、主な使い道は、複雑なシステムの部品の信頼を上げることだった。単体テストと同じ速さの枠で動かしていた。
  • 例ベースのテストと併用する：どの文書も、併用を勧める。

限界と注意

  • 性質を考えるのが難しい：聞き取り調査では、30人中16人が、性質を書く過程で作業が遅くなったと答えた。ある参加者は、最もよくある失敗は、何を検査するかが分からないことだと述べた。
  • 入力の偏りで空振りする：原典の論文の例では、「整列済みの一覧」を前提にすると、短い一覧に偏った。100件のうち、要素が2つ以上の一覧は19件だけだった（長さ0が49%、1が32%、2が12%、3が4%、4が2%、5が1%）。最良の対策は、専用の生成器とされた。前提が成り立つ入力が少ないと、「引数を使い切った」と報告される。
  • 欠陥のある場所を動かさないと通る：聞き取り調査では、生成器が意図した場合を作っておらず、欠陥を見逃した例があった。30人中11人は、テストの効き目を十分には考えていないと答えた。
  • 型を決めないと空振りする：QuickCheck の現行の文書は、型が決まらない性質が、対話環境で「（）」型として検査され、本来は失敗するはずの性質が通ってしまう例を挙げ、型を固定するよう勧める。
  • 通っても証明ではない：すべての入力は試せない。fast-check の文書は、入力を増やすほど、確信が高まる、と書く。
  • 絞り込みの無駄：作ってから捨てる絞り込みは、厳しいと無駄が多い（fast-check）。
  • 費用：proptest の文書は、複雑な値の生成は、QuickCheck より最大で1桁遅いことがある、と書く（proptest 自身の説明）。聞き取り調査では、時間の予算を超えないことが求められた。
  • 縮小の負担：値を小さくする関数を人が書く方式は嫌われ、書き間違えると、守るべき条件を壊して失敗した（聞き取り調査）。
  • 調査の範囲：聞き取り調査は1つの企業（OCaml を使う）の30人。他の環境で同じ結果になるとは限らない。

読むときの注意

  • 公式の文書と論文は、2026年11月8日時点で読んだ。ツールの機能や既定値は版で変わる。
  • 各ツールの説明は、それぞれの開発側の自己の説明。優劣の比較ではない。「ファジングはプロパティベーステストの一部」「縮小はこの手法に特有」といった説明は、fast-check 自身の見方。
  • 聞き取り調査の数字は、論文の人数のまま（たとえば、30人中16人）。1つの企業の結果。
  • 原典の論文に縮小の記述が見当たらないのは、語の検索で確認した範囲。
  • proptest の失敗の再現と、Hypothesis と fast-check の内部の仕組みは、読んでいない。
  • 比較表の軸と、前段・後段の分け方は、筆者の整理。
