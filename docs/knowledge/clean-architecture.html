クリーンアーキテクチャ：業務のルールを中心に置き、依存を必ず内側に向けて、画面・データベース・フレームワークから切り離す設計

Robert C. Martin が示したクリーンアーキテクチャについて、一言での説明、3行の要約、ヘキサゴナル・オニオン・従来の N 層との違い、前提になる考え方と使う側、具体的な仕組み（なぜ必要か、使いどころ、限界と注意）を、原典と各資料から整理する。

初回公開 2026-11-04 ／ 更新日 2026-11-04

一言で言うと

クリーンアーキテクチャは、業務のルールを中心に置き、ソースコードの依存を必ず内側に向けることで、画面、データベース、フレームワークから業務のルールを切り離す、ソフトウェアの設計の考え方です。

3行で表すと

  • 何であるか：Robert C. Martin が2012年に示した設計の考え方。ヘキサゴナル、オニオンなど、先行するいくつかの設計を、1つの図にまとめようとしたもの。
  • 何ができるか：画面、データベース、フレームワーク、外部のサービスから独立した、テストしやすい業務のルールを作れる。外側の部品を、業務のルールを変えずに入れ替えやすくなる。
  • 何が特徴か：同心円の層と、「依存性のルール」（ソースコードの依存は、内側にだけ向く）。内側から外側を呼ぶ必要がある所は、インターフェースで依存の向きを反転する。

類似するものと、違い

横のつながりです。どれも、業務のルールを、画面やデータベースの都合から守るための設計です。

提唱Robert C. Martin（2012年）Alistair Cockburn（2005年）Jeffrey Palermo（2008年）古くからの一般的な構成
核になる考え依存性のルール。依存は内側にだけ向くポートとアダプター。アプリを、利用者、プログラム、自動テスト、バッチのどれからも同じように動かせるようにする結合を中心に向け、中心にドメインモデルを置く。データベースは外部上から下へ呼び、依存も上から下へ向く
層の見せ方同心円（エンティティ、ユースケース、インターフェースアダプター、フレームワークとドライバー）。4つとは限らない六角形。内と外の違いを強調し、一次元の層の絵から離れる。窓口（ポート）の数だけ辺を使う玉ねぎの層。中心がドメインモデル横の層（UI、業務、データアクセス）
業務のルールの位置内側アプリケーションの内側中心中間の層。データアクセスの層に依存しやすい
  • 原典は、ヘキサゴナル、オニオン、Screaming Architecture、DCI、BCE を並べ、細部は違うが、とても似ていると書く。どれも、関心の分離が目的で、業務のルールの層と、インターフェースの層を持つ。クリーンアーキテクチャの図は、これらを1つの実践できる形にまとめる試み、と位置づけている。
  • 従来の N 層との違いは、依存の向き。N 層では、依存が上から下へ向くので、業務の層が、データアクセスの詳細（多くはデータベースの存在）に依存する。そのため、業務のルールをテストするのに、テスト用のデータベースが要ることが多い（Microsoft のガイドによる）。クリーンアーキテクチャでは、この依存を反転する。
  • Screaming Architecture（Martin、2011年）は、同じ著者の関連する考え方。アーキテクチャは、フレームワークではなく、システムのユースケースを語るべきで、ディレクトリの構成を見て「医療システム」と分かるべきだ、という主張。

前後で組み合わされるもの

縦のつながりです。前段と後段の分け方は、筆者の整理です。

前段：前提になる考え方

  • 依存性逆転の原則：境界をまたぐ依存の向きを反転する方法。原典も、オニオンの記事も、この原則に頼ると書く。
  • ドメイン駆動設計の考え方：Microsoft のガイドは、依存性逆転の原則とドメイン駆動設計に従うアプリケーションは、似た構造にたどり着くと書く。
  • ユースケースを中心にした設計：Ivar Jacobson の「Object Oriented Software Engineering」の副題は「ユースケース駆動のアプローチ」。Martin は、アーキテクチャは、ユースケースを支える構造だと書く。
  • 依存性の注入：実行時に、内側のインターフェースの実装を、外側のクラスから差し込む仕組み。Palermo も、Microsoft のガイドも、必要としている。

後段：これを使う側

  • 画面の構造：MVC の Controller、Presenter、View は、インターフェースアダプターの層に入る（原典）。
  • テストの方針：内側（業務のルール）は、外部の部品なしに単体でテストする。外側の実装（データベースなど）は、実際の外部と結ぶ統合テストで確かめる（Microsoft のガイド）。
  • 実装の足場：Microsoft のガイドは、このアーキテクチャのプロジェクト構成の参照アプリと、ASP.NET Core 向けのひな形を紹介している。
  • 位置づけ：Microsoft のガイドは、依存性の注入を備えた ASP.NET Core では、これを、小さくないモノリスの構造として、最も適したものと位置づけている。

具体的な仕組み

なぜ必要か

  • ヘキサゴナルの文書は、問題を次のように説明する。業務のロジックが、画面のコードの中に染み込む。すると、自動テストが書きにくくなり、人が使う形から、バッチやほかのプログラムが使う形へ移せなくなる。
  • 解決の試みとして、新しい層を作り、「今度こそ業務のロジックを入れない」と約束しても、違反を検出する仕組みがなければ、数年後に、その層が業務のロジックで散らかる、とも書く。
  • オニオンの記事は、画面が業務のロジックに結合し、その業務のロジックがデータアクセスに結合する、と問題を示す。間接的な依存も、依存である。
  • 原典が挙げる目標は、5つ。フレームワークから独立していること、テストしやすいこと、画面から独立していること、データベースから独立していること、外部の何物からも独立していること。

どう動くか

  • 同心円の4つの層：外側から、フレームワークとドライバー（データベース、Web のフレームワーク。書くのは、内側とつなぐ接着のコードくらい）、インターフェースアダプター（Controller、Presenter、View。データベースとの変換）、ユースケース（アプリケーション固有の業務のルール）、エンティティ（企業全体で通じる業務のルール）。内側ほど、方針（高いレベルの抽象）で、外側ほど、仕組み（具体的な細部）。層は4つとは限らない。
  • 依存性のルール：ソースコードの依存は、内側にだけ向く。内側にあるものは、外側にあるものの名前を、一切知ってはいけない。関数、クラス、変数も同じ。外側が作ったデータの形（フレームワークが返す行など）も、内側で使ってはいけない。
  • 境界をまたぐ流れ：処理の流れは、Controller から始まり、ユースケースを通って、Presenter で実行される。ところが、依存は、すべて内側のユースケースに向く。この食い違いを、依存性逆転の原則で解く。ユースケースは、内側にあるインターフェース（出力ポート）を呼び、外側の Presenter が、それを実装する。
  • 境界を越えるデータ：単純なデータ構造（構造体、データ転送用のオブジェクト、関数の引数）。エンティティや、データベースの行を、そのまま渡さない。内側にとって、最も都合のよい形で渡す。
  • 実行時：インターフェースの実装を、依存性の注入などで、内側のインターフェースにつなぐ。

使いどころ

  • 画面やデータベースを入れ替える見込みがあるとき。原典は、Web の画面を、業務のルールを変えずに、コンソールの画面に替えられる、と例に挙げる。
  • 業務のルールを、画面やデータベースなしに、速くテストしたいとき。
  • 業務のルールが小さくなく、長く使われるアプリケーション。Microsoft のガイドは、小さくないモノリスの構造として最も適すると位置づける。Palermo は、企業向けのアプリケーションの、ふだんの作り方として提案している。
  • 逆に、小さなアプリケーションでは、1つのプロジェクトに、画面も業務もデータアクセスも入れる構成でも、十分に役立つ、と Microsoft のガイドは書く。

限界と注意

  • 依存性のルールだけが決まり：層の数や、層の名前は、決まっていない（原典）。具体的な構成は、使う人の解釈に任される。流儀によって、構成にゆれが出る。
  • 実装の手間が増える：境界ごとに、インターフェースを置き、データを単純な形に変換する必要がある（原典の説明からの、筆者の整理）。実行時には、実装をつなぐ仕組み（依存性の注入など）も要る（Microsoft のガイド）。
  • 規則を守る仕組みが要る：ヘキサゴナルの文書が指摘するように、約束だけでは違反は検出されない。依存の向きを、レビューや自動の検査で確かめる運用が要る（筆者の整理）。
  • 小さなアプリケーションには、過剰になりうる（筆者の整理。Microsoft のガイドが、単一のプロジェクトでも十分な場合があるとする）。
  • フレームワークは敵ではない：Martin は、フレームワークを、使う道具であり、従う生き方ではないと書く。ただし、疑いの目で見て、どう使うか、どう身を守るかを考えるよう勧める。

  • Microsoft のガイドは、.NET のためのガイドで、「最も適している」という評価は、その文脈でのもの。
  • 比較表の軸（核になる考え、層の見せ方、業務のルールの位置）は、筆者の整理。優劣を示すものではない。
