ミューテーションテスト：コードに小さな欠陥を入れて、テストが気づけるかで、テストの質を測る手法

ミューテーションテストについて、一言での説明、3行の要約、コードカバレッジやツールとの違い、前後で組み合わされる仕組み、具体的な仕組み（なぜ必要か、使いどころ、限界と注意）を、各ツールの公式文書と3つの論文から整理する。

初回公開 2026-11-08 ／ 更新日 2026-11-08

一言で言うと

ミューテーションテストは、プログラムに小さな欠陥（変異）を自動で入れ、既存のテストがそれに気づいて失敗するかを調べることで、テストの検出力を測る手法である。

3行で表すと

  • 何であるか：ソースコードやバイトコードに、小さな変更（変異体）を自動で入れ、テストを実行して、テストの質を測る手法。
  • 何ができるか：テストが失敗すれば変異体は「殺された」、通れば「生き残った」。殺された割合（変異スコア）でテストの有効性を見積もれ、生き残った変異体は、テストが足りない場所と変更の中身を具体的に示す。
  • 何が特徴か：コードカバレッジが「実行されたか」だけを見るのに対し、「欠陥を検出できるか」を見る。代わりに、変異体の数だけテストを実行するので時間がかかり、元と同じ動きをする変異体（同値変異体）も混ざる。

類似するものと、違い

横のつながりです。同じ目的の指標であるコードカバレッジとの違いと、代表的なツールの違いを扱います。比較の軸は、筆者の整理です。

  • PIT の公式は、従来のカバレッジは、テストが実行したコードしか測れず、実行されたコードの欠陥をテストが検出できるかは確かめない、と書く。確実にテストされていないコードが分かるだけ、という説明。
  • 論文（FSE 2014）は、Java の5つのオープンソースのプログラムで、開発者が直した実際の欠陥357件を使い、テストが変異体を検出する力と、実際の欠陥を検出する力のあいだに、統計的に有意な相関があるとした。この相関は、コードカバレッジの影響を除いても残り、文のカバレッジと実際の欠陥の検出のあいだの相関より強い、と書く。

前後で組み合わされるもの

縦のつながりです。前段と後段の分け方は、筆者の整理です。

前段：ミューテーションテストが動くための土台

  • 通る状態の単体テスト：変異を入れる前に、元のコードでテストが全部通ることが前提。cargo-mutants は、変異の前に「baseline」としてテストを実行し、元から失敗していれば進まない。PIT のよくある質問にも、普段は通るテストが PIT では通らない原因（実行されるテストの範囲の違い、環境変数の違い、テストの順序への隠れた依存など）が挙がっている。
  • テストを動かす仕組み：PIT は JUnit か TestNG、mutmut は pytest、cargo-mutants は cargo test を使う。
  • ビルドの道具：PIT は Ant、Maven、Gradle などから動かす。コンパイル後のバイトコードを変異させるので、行番号とソースのファイル名の情報が残っている必要がある。
  • カバレッジの情報：PIT は、最初に行カバレッジを測り、変異した行を実行するテストだけを選ぶ。mutmut は、coverage.py の情報で、実行される行だけを変異させる設定もできる（既定は関数の単位）。

後段：結果を使う仕組み

  • レポート：PIT は、行カバレッジと変異のカバレッジを合わせた読みやすいレポートを出す。Stryker は、変更前後の差分と、どの演算子を使ったか、殺されたか生き残ったかを、文字で出す報告などを用意する。
  • テストの追加：生き残った変異体は、足りないテストの手がかり。Stryker の文書の例では、年齢が18以上かを調べる関数で、条件を常に真にする変異が生き残り、18未満を確かめるテストがおそらく足りない、と読む。
  • 除外と抑制：役に立たない変異体は、除外する。cargo-mutants は #[mutants::skip] で、PIT は、ログを呼ぶ行を既定では変異させないことで、避ける。
  • コードレビューやプルリクエストへの組み込み：PIT は、同じ作者の有償の拡張（arcmutate）で、プルリクエストやマージリクエストに対して自動で動かせる。Google は、コードレビューの中で、変更した行の変異体を開発者に見せている。

具体的な仕組み

なぜ必要か

  • テストは、書かれた行を実行するだけで、カバレッジを上げられる。極端な例は、アサーションのないテスト。PIT の文書は、そうしたテストは多くないが、コードの一部しか検査しないテストはよくある、と書く。Stryker の文書も、数字を上げるためだけのアサーションのないテストを例に挙げる。
  • そのため、カバレッジが高くても、テストが欠陥を見つけられるとは限らない。ミューテーションテストは、「欠陥を入れたら、テストは気づくか」を実際に試して、この差を埋める。
  • Stryker の文書は、パンにペーストを塗る例えを使う。カバレッジは、パンの80%にペーストが塗られていることを教える。ミューテーションテストは、それがチョコレートのペーストで、ほかの何かではないことを確かめる。

どう動くか

  • 流れ：（1）コードを解析して、変異を入れられる場所を見つける。（2）変異を1つ入れた版を作る。（3）テストを実行する。（4）判定する。（5）全部の変異体の判定から、変異スコアを出す。
  • 判定の種類：PIT は、殺された、生き残った、カバーなし（その行を実行するテストがない）、非実行可能（バイトコードが不正で、JVM が読み込めない）、タイムアウト（無限ループなど）、メモリエラー、実行エラーを分ける。cargo-mutants は、変異した版がコンパイルできないものを「unviable」（成立しない）として数える。
  • 変異の例：Stryker の文書は、年齢が18以上かを返す関数を挙げる。user.age >= 18 に対して、> や < に変える、false や true を返すように変える、といった変異体ができる。テストの結果は、変異体ごとに殺される場合と、生き残る場合がある。
  • 変異スコア：殺された変異体の割合（論文の定義：テストが元のプログラムと区別できる変異体の割合）。
  • 時間の抑え方：変更した部分だけを対象にする（PIT、Google）。変異した行を実行するテストだけを選ぶ（PIT）。同じ作業用ディレクトリを使い回して、差分のビルドを活かす（cargo-mutants）。中断しても続きから再開する（mutmut）。
  • Google の方式（論文）：変更したコードだけを、コードレビューの中で変異させる。変異体を1行につき最大1つに絞り、過去の結果から、役に立った演算子の変異を選ぶ。
  • 結合効果：変異分析の基本的な前提は、複雑な欠陥が、単純な欠陥の集まりと結びついていること（単純な欠陥をすべて検出するテストは、複雑な欠陥も検出する）。論文（FSE 2014）は、実際の欠陥357件のうち73%が、一般的な変異演算子の変異体と結びついていると報告した。

使いどころ

  • 変更したコードに絞って、頻繁に動かす。PIT の公式は、これがもっとも効果的な使い方だと書く。
  • 重要なロジックや、境界の条件が多い部分のテストが、本当に欠陥を検出できるかを確かめる。
  • コードレビューの中で、変更に対するテストの穴を示す。Google では、20億行のコードと、1日に5億回を超えるテストの実行の中で、この方式を実際に動かしている（論文による）。
  • 論文（ICSE 2021）は、約1,500万の変異体を分析し、ミューテーションテストを使う開発者は、より多くのテストを書き、生き残る変異体が減るように、質の高いテストでテストを改善していった、と報告する。また、過去の重要な欠陥の修正を調べ、その欠陥は変異体と結びついており、変異テストを使っていれば、生き残った変異体として示されて、防げた可能性があるとした。

限界と注意

  • 時間がかかる：全体の実行時間は、おおよそ、成立する変異体の数と、テストを1回実行する時間の積（cargo-mutants の文書）。PIT の文書も、計算量が大きく、規模とテストの速さによっては時間がかかると書く。
  • 同値変異体：変異しても動きが変わらない変異体がある。Stryker の文書は、2つの値が等しいときに結果が変わらない例を挙げ、これを自動で見つける確実な方法はなく、100%を目指さなくてよい、と書く。PIT も、ログのような、テストの対象にしない変更は、既定で避けると書く。
  • 役に立たない変異体：Google では、報告した変異体の85%が当初「役に立たない」と判断された（元と同じ動きをするか、検出できても、テストを足しても質が上がらないもの。例：コレクションの初期容量の変更）。ルールと選択を重ねて、役に立つ割合を15%から89%に上げた、と論文は書く。
  • 欠陥を全部は表せない：論文（FSE 2014）によると、実際の欠陥の17%は、どの変異体とも結びついていなかった。論文は、これを変異分析そのものの限界とする。
  • 変異スコアは、目標の数字ではない：Stryker の文書は、100%にならなくてもよいと書く。変異体の中には、テストする価値のないものも含まれる。
  • 使う環境の制約：mutmut は fork が使える環境が要る（Windows は WSL）。PIT は、バイトコードに行番号とソースのファイル名の情報が要る。

用語メモ

変異体（ミュータント）
元のプログラムに、小さな変更を1つ加えたもの。
変異演算子（ミューテーター）
どんな変更を加えるかの規則。たとえば、比較の向きを変える、足し算を引き算にする。
殺される／生き残る
変異体に対して、テストが失敗すれば「殺された」、すべて通れば「生き残った」。
変異スコア
殺された変異体の割合。
同値変異体
変更を加えても、元のプログラムと同じ動きをする変異体。
結合効果
複雑な欠陥が、単純な欠陥の集まりと結びついているという前提。
コードカバレッジ
テストが実行したコードの割合。
アサーション
テストの中で、結果が期待どおりかを確かめる記述。
バイトコード
Java のプログラムを、コンパイルして得られる中間の命令。
ベースライン（baseline）
変異を入れる前の、元のコードでのテストの結果。
