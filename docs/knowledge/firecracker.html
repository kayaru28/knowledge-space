Firecracker：コンテナの速さと、仮想マシンの安全性を両立させる、AWS の軽量な仮想マシン

AWS が作った軽量な仮想マシンモニター Firecracker について、一言での説明、3行の要約、類似の技術との違い、前後で組み合わされる仕組み、具体的な仕組み（なぜ必要か、使いどころ、限界と注意）を、公式の文書と論文から整理する。

初回公開 2026-11-04 ／ 更新日 2026-11-04

一言で言うと

Firecracker は、複数の利用者の処理を同じマシンで安全に動かすために、機能を絞り込んだ軽量な仮想マシン（microVM）を、素早く作って動かす仮想マシンモニターです。

3行で表すと

  • 何であるか：Linux の KVM を使って microVM を作る、オープンソース（Apache 2.0）の仮想マシンモニター（VMM）。AWS が、AWS Lambda と AWS Fargate のために作った。
  • 何ができるか：1つのプロセスが1台の microVM を受け持ち、API で設定して起動する。仕様では、1 CPU・128 MiB の構成で、起動の指示から Linux の最初のプロセスまでが 125 ミリ秒以下、VMM のメモリの上乗せが 5 MiB 以下。
  • 何が特徴か：BIOS や古い周辺機器を持たず、機能を最小限にして攻撃されうる面を減らし、さらにプロセスの制限（seccomp、jailer）を重ねることで、仮想化の隔離と、コンテナに近い軽さを両立させる。

前後で組み合わされるもの

縦のつながりです。前段と後段の分け方は、筆者の整理です。

前段：Firecracker が動くための土台

  • Linux の KVM：Firecracker は、KVM とプロセッサの仮想化機能に依存して、隔離を実現する。Linux のホストと Linux のゲストで動く。
  • ホストの設定：隔離と多層防御は、ホストの設定が適切であることが前提。公式の文書は、ホストとゲストのカーネルと、CPU のマイクロコードを定期的に更新すること、seccomp の制限を弱めないこと、シリアルの出力の扱いなどを、本番の推奨として挙げている。
  • jailer：本番では、Firecracker を `jailer` という別のプログラム経由で起動する。jailer は、権限の要る設定（cgroup、chroot など）をしてから、権限を落とし、Firecracker を実行する。
  • ゲストのカーネルとルートファイルシステム：最小の構成では、ゲストのカーネルと、1つのルートのブロックデバイスを指定すれば足りる（論文による）。
  • ホストのネットワークとストレージ：ネットワークは、ホストの TAP デバイスが受け、ブロックデバイスは、ホストのファイルが支える。

後段：Firecracker を使う上位の仕組み

  • AWS Lambda と AWS Fargate：Firecracker が作られた目的。公式 README が、本番で使われていると書く。
  • Kata Containers と Flintlock：Firecracker を組み込んだコンテナのランタイム・管理の仕組みとして、公式 README が挙げている。Flintlock は、Firecracker と Cloud Hypervisor のどちらかを microVM ごとに選べる。
  • firecracker-containerd：コンテナのランタイム containerd で、Firecracker の microVM を管理する。公式リポジトリの README が挙げる使い道は、信頼できない第三者のコンテナを専用の microVM に隔離すること、隔離を保ちながら多様なコンテナを同じホストに詰めること。
  • Kubernetes や Docker などのコンテナの道具：論文は、これらを Firecracker の上位の仕組みとして想定している。

具体的な仕組み

なぜ必要か

  • 論文の説明では、従来は選択肢が二つに分かれていた。仮想化は隔離が強いがオーバーヘッドが大きく、コンテナは軽いが隔離が弱い。
  • サーバーレスやコンテナのサービスは、複数の顧客の処理を同じハードウェアで動かす（マルチテナント）。そのため、セキュリティと性能の両面の隔離が要る。同時に、関数やコンテナをミリ秒の単位で用意できることも求められる、と論文は書く。
  • Firecracker は、この二者択一をしたくないために作られた、と論文は書く。

どう動くか

  • 1プロセスに1台の microVM。プロセスの中には、API のスレッド、VMM のスレッド、vCPU のスレッド（ゲストの CPU の数だけ）がある。API のスレッドは、仮想マシンの高速な処理経路には入らない。
  • 使う前に、API で microVM を設定する（vCPU の数、メモリの大きさ、ネットワーク、ディスクなど）。そのあとに起動の指示（`InstanceStart`）を出す。
  • 見せる機器は最小限：virtio のネットワークとブロック、vsock、シリアルのコンソール、リセット用の簡易なキーボードコントローラー。そのほか KVM が提供する割り込みコントローラーとタイマー。
  • レート制限：ディスクとネットワークごとに、トークンバケット方式で、転送量と操作の回数を制限できる。
  • メタデータ：microVM の中から、ホストが設定したデータを読む軽い仕組み（MMDS）がある。
  • 多層防御：KVM の仮想化の境界が最初の層。そのうえで、Firecracker が自動で入れる seccomp のフィルター（許すシステムコールを最小に絞る）、cgroup と名前空間による資源の隔離、jailer による権限の低下を重ねる。公式の設計文書は、ゲストの vCPU のスレッドを、動き始めた時点で悪意のあるコードを実行していると見なし、信頼のゾーンを入れ子にして封じ込める考え方を取る。
  • スナップショット：動いている microVM の状態を保存し、あとで別のプロセスで再開できる。差分のスナップショットは、開発者向けのプレビューの段階。

使いどころ

  • サーバーレスの関数や、コンテナのサービスなど、多数の短命な処理を、隔離を保ちながら高密度に動かす場面（AWS Lambda、AWS Fargate が実例）。
  • 信頼できないコードの実行：第三者のコンテナなどを、専用の microVM に閉じ込める（firecracker-containerd の例）。
  • Kubernetes のノードを microVM にする、など、軽い仮想マシンを大量に作る用途（Flintlock の例）。
  • 目安となる仕様：1 CPU と 128 MiB のメモリの microVM を、約5台/秒/コアの速さで作れる。36コアのホストで、毎秒180台という例を、設計文書は挙げている。

限界と注意

  • 機能を絞っている：論文によると、BIOS を持たず、任意のカーネルを起動できず、古い周辺機器と PCI をエミュレートせず、仮想マシンの移動（マイグレーション）に対応しない。Windows は、大きな変更なしには起動できない。ここは2020年の記述で、その後、virtio の PCI 機器のホットプラグが開発者向けのプレビューとして加わっている。最新の仕様は、公式の README と文書を見る。
  • 隔離は、設定に依存する：公式の文書は、安全にマルチテナントで使えるかは、適切に設定された Linux のホストに依存すると明記している。推奨の設定を実施しないと、保証は成り立たない。
  • 通信の制限はしない：Firecracker はネットワークの通信を絞らない。ゲストの外向きの通信はすべて信頼できないものとして扱い、ホスト側で絞る必要がある。
  • スナップショットの再利用：同じ状態から2回以上再開すると、乱数の種、識別子、暗号の情報など、本来は一意であるべきものが重複しうる。公式の文書は、一意性を守る仕組みなしにこの使い方をするのは安全でないと考える。再開のあと、ネットワークとの接続が保たれる保証もない。
  • カーネルの対応：検証されたホストとゲストのカーネルの版にしか、保証がない。公式の方針は、一度追加した版を最低2年は支える。
  • 移植性：論文は、Firecracker がホストの OS の間の移植性を犠牲にしていると書く。

読むときの注意

  • 論文は2020年の発表で、数字（行数、機能の有無）はその時点のもの。公式の README と文書は、2026年11月4日時点で読んだ。
  • 仕様の数値は、AWS の特定のインスタンス上で、会社が測る条件での保証で、ほかの環境では変わりうる。
  • 比較表の軸（隔離のしかた、方針）は、筆者の整理。各プロジェクトの公式の README の説明にもとづくが、優劣を示すものではない。
  • Firecracker の最新の版は、変更履歴によると 1.17.0（2026年11月4日に確認）。機能や制約は版で変わる。

用語メモ

microVM
機能を最小限にした、軽量な仮想マシン。
仮想マシンモニター（VMM）
仮想マシンを作って動かすプログラム。ハイパーバイザーの一部として、機器のエミュレーションなどを受け持つ。
KVM
Linux のカーネルに組み込まれた、ハードウェアの仮想化機能。
jailer
Firecracker を権限の少ない状態で起動するための、補助のプログラム。
seccomp
プロセスが使えるシステムコールを制限する Linux の仕組み。
virtio
仮想マシンと、ホストの機器をつなぐ標準の仕組み。ネットワークやディスクに使う。
TAP デバイス
仮想のネットワークインターフェース。microVM の通信を、ホストのネットワークにつなぐ。
vsock
ホストと仮想マシンのあいだの通信の仕組み。
MMDS
microVM の中から、ホストが設定したメタデータを読む仕組み。
マルチテナント
複数の利用者が、同じ設備を共有して使うこと。
サーバーレス
サーバーの管理を意識せず、関数などの小さな処理を、必要なときだけ動かす使い方。
トークンバケット
転送量や操作の回数を、一定の速さで制限するアルゴリズム。
