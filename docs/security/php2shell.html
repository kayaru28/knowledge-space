PHP の緊急の脆弱性「PHP2Shell」：Web の土台に10年以上ひそんだ欠陥と、公開前夜の混乱

2026年10月21日に修正版が出た PHP の脆弱性2件（CVSS 9.2）について、壊れた状態が次のリクエストに引き継がれる仕組み、対象のバージョンと軽減策、AI の道具を使った発見から公開までの年表、情報の漏れで前倒しになった公開前夜と国内の緊急メンテナンスを、公式の発表から図で整理する。

初回公開 2026-10-22 ／ 更新日 2026-10-22

ひとことで言うと

2026年10月21日の日本時間23時、PHP の開発チームは、認証なしに外部からサーバー上でプログラムを動かされるおそれのある脆弱性2件（CVE-2026-109618、CVE-2026-109619）を直した PHP 8.5.12／8.4.27／8.3.36／8.2.35 を公開しました。どちらも CVSS v4.0 で 9.2（緊急）です。2つを合わせて「PHP2Shell」と呼ばれています。

原因は、メモリ不足などで処理が途中で止まったときに壊れた状態が残り、同じワーカーが次のリクエストでそれを使ってしまうことです。PHP の中心の部分にあるため、アプリケーションの作りに関係なく影響します。修正の公開は、CVE 番号が漏れたため1日前倒しされました。国内では、修正の公開を待たずに緊急メンテナンスに入るサービスが相次ぎました。

何が起きるのか

PHP では、1つのワーカー（PHP を動かすプロセス）が、多くのリクエストを順に処理します。今回の2件は、どちらも「前のリクエストの後片付けが不完全なまま、次のリクエストに進んでしまう」ことが原因です。

PHP の開発チームによると、影響を受けるのは、Web のリクエストを処理するすべての PHP です（PHP-FPM、Apache の mod_php、php-cgi、FrankenPHP、LiteSpeed）。危険が最も高いのは mod_php です。

対策

完全な対策は、修正版への更新だけです。Linux のディストリビューションと長期サポートの業者は、事前に修正を受け取っています。

すぐに更新できないときに、特定の攻撃の経路を減らす設定も示されています。ただし、PHP の開発チームは、どれも「安全にするものではない」としています。

脆弱性軽減策

CVE-2026-109619
（古い状態の残り）		session.upload_progress.enabled=0 にして、すべてのワーカーを再起動する／PHP 8.5 では fatal_error_backtraces=0 にする／リクエストごとに当てている無効な設定を取り除く／攻撃者が起こせる致命的なエラーや時間切れを直す

IPA は、すぐに直せない場合の考え方として、サポート状況の確認、暫定対策とアクセス制限、必要なら外部からのアクセスの遮断やサービスの一時停止、経営層を含めた体制の検討、移行や廃止も含めた方針の決定を挙げています。製品や機器の内部で PHP が使われていて、利用者からは見えない場合があることにも注意を促しています。Wiz は、攻撃の兆しとして、メモリの上限のエラーや HTTP 500 が続く不審なリクエスト、異常に大きいか形の崩れた PHPSESSID の Cookie、説明のつかないワーカーの入れ替わりを挙げています。

見つかるまで

欠陥そのものは10年以上前からありました。2024年の外部の監査をきっかけに兆しは見つかっていましたが、修正は何か月も止まっていました。2026年夏、AI の道具を使った複数の調査が、同じ原因から攻撃できることを示しました。

公開前夜の混乱

PHP Foundation によると、協調した開示は、予定日の2日前まではうまくいっていました。そこから、情報の漏れや先行公開が重なりました。
