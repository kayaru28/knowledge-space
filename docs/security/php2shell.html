PHP の緊急の脆弱性「PHP2Shell」：Web の土台に10年以上ひそんだ欠陥と、公開前夜の混乱

2026年10月21日に修正版が出た PHP の脆弱性2件（CVSS 9.2）について、壊れた状態が次のリクエストに引き継がれる仕組み、対象のバージョンと軽減策、AI の道具を使った発見から公開までの年表、情報の漏れで前倒しになった公開前夜と国内の緊急メンテナンスを、公式の発表から図で整理する。

初回公開 2026-10-22 ／ 更新日 2026-10-29

ひとことで言うと

2026年10月21日の日本時間23時、PHP の開発チームは、認証なしに外部からサーバー上でプログラムを動かされるおそれのある脆弱性2件（CVE-2026-109618、CVE-2026-109619）を直した PHP 8.5.12／8.4.27／8.3.36／8.2.35 を公開しました。どちらも CVSS v4.0 で 9.2（緊急）です。2つを合わせて「PHP2Shell」と呼ばれています。

原因は、メモリ不足などで処理が途中で止まったときに壊れた状態が残り、同じワーカーが次のリクエストでそれを使ってしまうことです。PHP の中心の部分にあるため、アプリケーションの作りに関係なく影響します。修正の公開は、CVE 番号が漏れたため1日前倒しされました。国内では、修正の公開を待たずに緊急メンテナンスに入るサービスが相次ぎ、首相も X でパッチの適用やサイトの一時停止を呼びかけました。

その後、Amazon が公開の4日前の10月17日に悪用の試みを観測していたと報告しました。Cloudflare では、公開のあと悪用の試みが数時間で桁ごとに増え、数百万件に達しています。

10月26日には、米国の CISA が2件を「悪用が確認された脆弱性のカタログ」に加え、JPCERT/CC は、実証コードの公開と悪用を試みる通信の報告が相次いでいるとして、改めて更新と侵害の調査を求めました。PHP の開発チームは、条件のまれな3つ目の脆弱性（CVE-2026-115560）も公表しています（10月27日追記）。10月27日の Wiz の観測では、脆弱な機器は1週間で約3分の2減った一方、同社のおとりで最後まで成功した例は見ていないとされています（10月28日追記）。

何が起きるのか

PHP では、1つのワーカー（PHP を動かすプロセス）が、多くのリクエストを順に処理します。今回の2件は、どちらも「前のリクエストの後片付けが不完全なまま、次のリクエストに進んでしまう」ことが原因です。

PHP の開発チームによると、影響を受けるのは、Web のリクエストを処理するすべての PHP です（PHP-FPM、Apache の mod_php、php-cgi、FrankenPHP、LiteSpeed）。危険が最も高いのは mod_php です。

対策

完全な対策は、修正版への更新だけです。Linux のディストリビューションと長期サポートの業者は、事前に修正を受け取っています。

すぐに更新できないときに、特定の攻撃の経路を減らす設定も示されています。ただし、PHP の開発チームは、どれも「安全にするものではない」としています。

IPA は、すぐに直せない場合の考え方として、サポート状況の確認、暫定対策とアクセス制限、必要なら外部からのアクセスの遮断やサービスの一時停止、経営層を含めた体制の検討、移行や廃止も含めた方針の決定を挙げています。製品や機器の内部で PHP が使われていて、利用者からは見えない場合があることにも注意を促しています。Wiz は、攻撃の兆しとして、メモリの上限のエラーや HTTP 500 が続く不審なリクエスト、異常に大きいか形の崩れた PHPSESSID の Cookie、説明のつかないワーカーの入れ替わりを挙げています。

見つかるまで

欠陥そのものは10年以上前からありました。2024年の外部の監査をきっかけに兆しは見つかっていましたが、修正は何か月も止まっていました。2026年夏、AI の道具を使った複数の調査が、同じ原因から攻撃できることを示しました。

公開前夜の混乱

PHP Foundation によると、協調した開示は、予定日の2日前まではうまくいっていました。そこから、情報の漏れや先行公開が重なりました。

公開の前から始まっていた悪用

Amazon は10月22日、おとりのサーバー網（MadPot）で、公開の4日前の10月17日に PHP2Shell の悪用の試みを観測していたと報告しました。匿名化の通信網からの試みで、攻撃者がどうやって公開前に情報を得たかはわかっていません。公開の日の10月21日も、日本時間11時ごろから実証コードがいくつも出回り、11時〜17時に複数の攻撃者とみられる試みがありました（実際のシステムで成功したかは分析中）。公開のあとは、広く悪用されています。

Amazon は、教訓として次の3つを挙げています。公開日を悪用の始まりとみなさないこと（PHP2Shell では少なくとも10月17日から調べる）。インターネットに面したシステムの重大な脆弱性は、修正や軽減の目安を「日」ではなく「時間」で考えること。特定の CVE に頼らない検知に投資すること。AI を使った分析で、修正の差分や注意喚起から攻撃のコードを作る手間が下がっているためです。

JPCERT/CC は10月22日の注意喚起で、修正の適用に加え、侵害の有無を調べるよう求めました。調べる点は、不自然に長いか形の崩れた PHPSESSID の Cookie、不審な multipart/form-data のリクエストとその前後のメモリ上限のエラーや HTTP 500、ワーカーの予期しない終了や頻繁な再起動です。痕跡がなくても、攻撃を受けていないとは言い切れないとしています。

公的機関の勧告と、悪用の確認（10月27日に追加）

米国の CISA（10月21日付の勧告）

「php2shell」の2件を直ちに修正するよう強く求めた。更新できない場合や PHP 8.1 以前のサポート外のバージョンを使い続ける場合は、修正されるまで PHP を使うシステムをオフラインにするよう求めている。WAF（Web アプリケーションファイアウォール）は更新までの一定の保護になりうるとしている。見る点は、PHP のワーカーがシェルを起動したり、ツールをダウンロードしたりしていないか。10月23日に検知ルール（SIGMA）と協力機関の資料（米 NSA、英 NCSC、豪 ACSC、オランダ NCSC）を追加した。10月26日には、2件を「悪用が確認された脆弱性のカタログ（KEV）」に加えた。

JPCERT/CC（10月26日の追記）

実証コードが多数公開され、悪用を試みる通信を観測したという報告も相次いでいる。一方、実証コードで実際に任意のコードを実行できるかは、PHP のバージョン、実行環境、メモリ配置などの条件によって決まり、環境に応じた調整が必要だとしている。今後も、実証コードや新しい攻撃手法の公開、特定の環境を狙う攻撃の開発が進む可能性があるため、修正版への更新と侵害の調査を求めている。

PHP 開発チーム（10月23日）：3つ目の CVE-2026-115560

条件が珍しい脆弱性。session.serialize_handler を設定で php_binary か php_serialize にしたうえで、実行時に ini_set() で php に切り替えて session_start() を呼び、さらにセッションのアップロード進捗（session upload progress）が有効なときに起こりうる。実際にはまれな構成なので、通常のリリースサイクルで直し、全文の勧告は次のリリースで出すとしている。それまでの緩和策は、session.upload_progress.enabled=0 にして全ワーカーを再起動すること（CVE-2026-109619 の緩和策と同じで、すでに適用していれば追加の対応は不要）。

PHP 開発チーム（10月26日）：Windows 版の再ビルド

PHP 8.5.12-1、8.4.27-1、8.3.36-1、8.2.35-1 を公開。Brotli 1.2.1 を含み、Brotli の展開処理の境界外書き込み（CVE-2026-111497）を直している。この欠陥には、cURL 拡張で HTTP レスポンスの自動展開を有効にしたときに届く（既定では無効だが、アプリケーションや HTTP クライアントのライブラリが有効にすることがある）。PHP のバージョンは変わらず、依存ライブラリだけを更新したビルド。Brotli の件は、別のまとめ「Brotli のデコーダー」を参照。

筆者の整理：公開（10月21日）から5日後の10月26日に、米国が「悪用が確認された」と公式に位置づけた。観測の報告（Amazon、Cloudflare）と、公的機関の確認には時間差がある。一方、JPCERT/CC は、実証コードが出回っていても、実際に動くかは環境に左右されるとしている。「悪用の試みがある」と「自分の環境で成り立つ」は別の話で、どちらの場合も修正版への更新が対策になる。Wiz の1週間後の観測は、この差を数字で示した。試みは見えるが、最後まで成功した例は見ていない。しかし、環境に合わせて作り込まれた攻撃は成り立ちうる、というのが同社の見立てで、障壁は下がると予想されている。

公開から1週間の状況（10月28日に追加）

Wiz の観測（10月27日）：脆弱な機器は減っている

公開（10月21日）から数日で、PHP2Shell の影響を受けたままインターネットに公開されている機器の1日あたりの数は、約67%減った。脆弱なインスタンスを1つ以上公開していた組織の数は、約47.9%減った。公開から1週間の時点で、当初影響を受けた組織の53%未満が、脆弱なままだった。Wiz は、修正の適用、アップグレード、機器の廃止、公開の制限が合わさった結果と見ていて、どの対策の寄与が大きいかは、このデータでは分からないとしている。PHP は、Wiz のデータの65%の組織で使われている。また、公式の修正が出ない PHP 7.3 以前を使う機器の割合は、5日間で8.3%から5.7%に下がった。

Wiz の観測：悪用の試みは見えるが、最後まで成功した例は見ていない

Wiz のおとり環境で観測した悪用の試みは、限られた数だった。公開されている実証コードのうち、任意の相手に最後まで通用する完全なものは見つかっていない、と述べる。ただし、複数の相手に通用する攻撃を、提携先から非公開で受け取っているとも書いている。観測した試みは、2種類のオープンソースの攻撃キットによるもので、どちらも最後の段階までは進まなかった。古い型は、リクエストの大きさの上限（8MB）に阻まれた。新しい型は、メモリ不足を起こすところまで進んだが、次の段階のメモリ内容の読み出しに失敗した。最後の段階を送った例はなかった。

なぜ失敗するのか（Wiz の分析）

攻撃は、連続するリクエストを同じワーカーに届ける必要がある。PHP のビルドやメモリの上限が違うと、メモリの配置が変わって、読み出しが成り立たない。通信の遅れや時間切れでも、連鎖が途切れる。Wiz は、公開されている実証コードをそのまま大量に実行しても、環境ごとの調整が要るため、運用できる道具にはならないとする。ただし、この障壁は時間とともに下がると見ていて、専門性のある攻撃者は、調整して頑丈な道具を作れるとしている。

「PHP2Shell」を名乗る別の道具

PHP2Shell と名づけられているが、今回の2件を突いていない道具も観測された。古くからあるセッション汚染の手法と、アプリケーション側の別の欠陥（ローカルファイルの読み込み）を前提にしたもの。別の欠陥がなければ動かない。

Wiz の結論

Wiz 自身の観測では、最後まで成功した例はまだない。一方、ある研究者がおとり環境で公表した報告が、攻撃の通信、メモリの漏えい、その後のコード実行を結びつけた、これまでで最も強い公開の証拠と位置づけている。ただし、そのおとりは、Apache の mod_php で、ワーカーが1つだけという、攻撃に有利な設定だった。ほかの環境で同じように成り立つことは示していない。Wiz は、このおとりの結果が、CISA が悪用の確認済みに加えた一因だった可能性が高いとしている。短期でも長期でもリスクは残るので、更新や別の方法での対処は必要、というのが結論。

IPA（10月27日の更新）

CISA の KEV への掲載（10月26日）を追記した。IPA は、国内での攻撃被害の事例は把握していない、としたうえで、対策済みのバージョンへの移行を改めて求めている。

Palo Alto Networks（10月21日公開、10月28日更新）

PAN-OS が影響を受ける。深刻度は9.2（緊急）、緊急度は最高、攻撃の成熟度は「攻撃されている」。PAN-OS 12.2 は 12.2.4-h1 以降が修正版。12.1 系は 12.1.4-h13（予定は10月29日）、12.1.7-h11、12.1.10-h3（予定は10月30日）で、11.2 系などにも修正版が順次出る。Cortex、GlobalProtect アプリ、Cloud NGFW などの製品は影響を受けない。

NEC の Aterm（10月26日公開、10月28日更新）

Aterm の製品とサービスは、この脆弱性の影響を受けない、と確認した。一部の機種では、クイック設定の画面の URL に「/index.php」と出るが、末尾に「.php」とあるだけで、ソフトウェアは PHP を使っていない。

筆者の整理：欠陥は10年以上前からありました。PHP Foundation と Wiz はどちらも、攻撃に使える形にするには複雑な手順が必要だったが、AI の道具がその壁を下げたとしています。守る側では、公開の前に情報の一部が漏れ、準備の時間が縮みました。さらに、悪用の試みは公開日より前に始まっていました。公開日を「悪用の始まり」とみなさず、それより前から侵害を調べる必要があります。更新できない古い PHP を使い続けている仕組みは、IPA の言うとおり、廃止も含めた判断が必要になります。
