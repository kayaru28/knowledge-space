Workers AI で他の顧客の要求の内容が応答に混ざった：Cloudflare の GLM-5.3 の事案を、原因から対処まで詳しく読む

2026年8月27日から9月9日まで、Cloudflare の Workers AI（GLM-5.3）で、他の顧客の要求の内容が応答に混ざった事案について、設定のミスと推論エンジンの不具合の仕組み、時系列、対処、上流の修正、同じ種類の別の不具合、運用者への推奨を、公式の報告から整理する。

初回公開 2026-11-05 ／ 更新日 2026-11-05

ひとことで言うと

2026年8月27日から9月9日までの約2週間、Cloudflare の AI 推論サービス「Workers AI」で、GLM-5.3 のモデルに非常に長いプロンプトを送ると、直前に別の顧客が同じモデルに送った要求の内容が混ざった応答が返ることがありました。155件です。

原因は、設定のミスと、推論エンジン（SGLang）の不具合が重なったことです。共有されていたのは、キャッシュの内容ではなく、メモリの領域（ページ）で、消去されないページの、書き込まれていない部分を読んでしまったことが、漏えいの正体でした。

何が起きたか

  • 9月8日の23時11分（世界協定時）、セキュリティ研究者から、Cloudflare の脆弱性報告制度（HackerOne）を通じて、「GLM-5.3 に非常に長いプロンプトを送ると、ほかの利用者のセッションのテキストが返ることがある」という報告を受けた。
  • 9月9日に、報告を検証し、2つの独立したアカウントで25分以内に再現して、事案を宣言した。モデルを非公開にし（要求には HTTP 400 を返す）、原因を特定して、設定の修正とエンジンのパッチを入れ、同日の19時40分に復旧した。
  • 8月27日から9月9日までの間に、少数の顧客が、同じモデルへの直前の他の顧客の要求の内容を含む応答を受け取った。合計155件で、すべて 681,280 トークンを超えるプロンプトへの応答だった。
  • 研究者と自社のテストを除くと、見つかった要求は、通常の長い文脈の使い方と、時期も量も一致していて、故意に悪用された証拠は見つからなかった。
  • ほかの Workers AI のモデルは、影響を受けていない。
  • 公開は10月26日。報告した研究者と、推論エンジン SGLang の開発元との、連携した公開（コーディネートされた開示）として出された。

よくある疑問：キャッシュが顧客で共通化されていたのか

  • 共有されていたのは、キャッシュの内容ではなく、メモリの領域（ページ）。全顧客の要求が、同じ GPU のメモリのページのプールから割り当てを受けるのは、設計どおり。
  • 使い終えたページは、ゼロに消去されない。次の要求が、上書きするだけ。原典は、これを推論エンジンで一般的な方式で、最高の性能を出すのに必要だと書く。そのため、ページの所有権の管理は、エンジンの責任になる。
  • 今回の事故は、他の顧客のキャッシュを「共有して再利用した」ものではなく、確保した領域の、書き込まれていない部分に、前の要求の残りが残っていて、それを読んでしまったもの。
  • つまり、消去しない設計と、拒否の見落としが重なって、顧客の境界を越えて内容が漏れた。

仕組みの前提

  • KV キャッシュ：AI モデルが文章を作るとき、それまでの文脈の計算結果（キーと値）を、GPU のメモリに置いておく仕組み。長い文脈ほど大きい。
  • 分離構成（プレフィルとデコード）：Workers AI は、GLM-5.3 を、プロンプトを処理して KV キャッシュを作る GPU の群（プレフィル）と、それを受け取って応答を生成する GPU の群（デコード）に分けて動かしている。KV キャッシュは、RDMA（別のマシンのメモリに直接書き込む仕組み）で、プレフィルからデコードへ渡される。
  • ページのプール：KV キャッシュは、固定サイズのページに分かれたプール。要求は、受け付けられるとページを割り当てられ、終わると返す。
  • 領域の大きさは設定値ではない：SGLang は、モデルの重みを読み込んだあとに残った GPU のメモリから、起動時に領域の大きさを決める。モデルの文脈の長さは、別の設定値で、2つが一致する保証はない。一致を確かめるのは、運用する側の仕事。

事故の流れ（原因の連鎖）

  • 設定のミス：文脈の長さ 1,048,576 トークンに対して、プレフィルの領域は 681,280 トークンぶんしかなかった。Cloudflare は、開始前にこの不一致を知っていたが、エンジンが、収まらない要求にはエラーを返すと考えた。長い文脈の試験でも、成功の応答が返ったので、問題ないと判断した。
  • 試験の穴：試験は、応答の状態コードと性能だけを見て、モデルの出力の中身や一貫性は確かめていなかった。
  • エンジンの不具合：領域に収まらない要求は、受付で「拒否」として印が付き、プロンプトが1トークンの代わりの文面に差し替えられる。1台で動かす構成では、これで要求が正しくエラーで終わる。
  • 分離構成での見落とし：プレフィルとデコードの受付は、要求が「終わったか」だけを見て、「拒否されたか」を見ていなかった。拒否された要求は、まだ生きている要求として通ってしまった。
  • 通ったあとの流れ：
    1. ルーターが、デコードに、元のプロンプトの長さ（例では8ページ）を知らせ、デコードは8ページを確保した。
    2. プレフィルは、差し替えられた1トークンぶんだけを計算し、1ページぶんの KV キャッシュを転送して、「転送完了」を通知した。
    3. デコードは、プレフィルが全ページを書き込んだと思い込み、応答の生成を始めた。
    4. 確保した8ページのうち、書き込まれたのは1ページだけ。残りの7ページには、前の要求が残したデータ（他の顧客のプロンプトや、途中の生成）が、そのまま残っていた。
    5. デコードは、8ページすべてを読んで応答を作り、HTTP 200 で返した。
  • 外から見える特徴：応答の `prompt_tokens` は、長いプロンプトの長さと一致し、文章は筋が通っていた。ただし、8ページぶんのプレフィルにかかるはずの時間より、速く返ってきた。内容には、他の利用者のページの内容が含まれていた。
  • 閾値を超える要求は、すべてこの経路を通った。タイミングの偶然ではなく、毎回起きる不具合だった。
  • 上流への報告：同じ不具合は、7月6日に、別の利用者が SGLang に報告していた。Cloudflare は、この事案の調査中に気づいた。

Cloudflare の対処

  • 即時の対処（9月9日）：
    • 領域を、文脈の長さ全体が入る大きさにした。GLM-5.3 の設定を、GLM-5.2 の設定に合わせ、GPU のメモリが空いた結果、プレフィルの領域は約204万トークン（文脈の長さの約2倍）になった。文脈に収まる要求が、必ず領域にも収まるので、拒否の経路には入らない。これだけで、不具合は起きなくなる。
    • エンジンのパッチ：拒否された要求を、受付の段階で、元のエラーとともに終了させる。領域の大きさだけに頼るのは壊れやすい（量子化、並列化の設定、モデルの版などで、領域の大きさが簡単に変わる）うえ、ほかにも拒否が起きる場面がありうるため。上流への提案には、デコード側が、転送されたトークン数と、確保した数が一致するかを確かめる仕組みも含まれた。
    • 検証：研究者の再現用のスクリプトと、自社の目印（カナリア）を入れた試験で確かめてから、モデルを戻した。
  • 9月11日〜19日の追加の強化（すべての本番の構成に）：
    • 解放の遅延を、転送元（プレフィル）のページにも広げ、中止だけでなく、あらゆる失敗に対応させた。
    • 転送の1回の呼び出しの大きさに上限（バッチの上限）を設け、1回の呼び出しが、解放の待ち時間を超えないようにした。
    • ロードバランサーを変えて、クライアントの切断が、転送の途中の中止を引き起こさないようにした（プレフィルは終わるまで、デコードは最初のトークンまで、接続を保つ）。
    • 分離構成の変更のたびに、領域の大きさと文脈の長さの照合、解放の遅延、転送のバッチの上限、必要なパッチが入っているかを、チェック項目にした。
  • 同じ分離構成の、ほかのモデルは、領域が文脈の長さより大きいので、拒否の経路に入らない。エンジンの修正と強化は、SGLang で動かすすべてのモデルに入れた。

上流（SGLang）の対応

  • 受付の修正：拒否された要求を、受付の段階（プレフィルとデコードの待ち行列に入る前）で終了させ、エラーを返す。9月16日に取り込まれた。それ以前の修正は、プレフィルの結果を処理した時点で終了させるものだった。
  • 影響の範囲：SGLang は、この拒否の経路は、分離構成のときだけ、1台で動かす構成ではエラーが返ると説明する。
  • 上流の版：Cloudflare は、この不具合の修正が v0.5.20 で出て、v0.5.21 と v0.5.22 で続けて直されたと書き、すべての運用者に、v0.5.22 以降への更新を強く勧めている。

同じ種類の別の不具合：中止された転送の競合

Cloudflare の報告も、SGLang の記事も、今回の不具合と同じ「KV キャッシュの領域の管理の不具合」の別の形を、あわせて説明している。今回の事案の原因ではない（今回は、拒否された要求が毎回通ることが原因）。

対策として、次の仕組みが入った。

  • 仕組み：分離構成では、プレフィルが、デコードの領域に、RDMA で書き込む。要求が途中で中止されると（クライアントの切断、タイムアウト、転送の障害など）、すでに送り出した書き込みは、取り消せない。
  • 競合：デコードが、中止された要求の領域を、すぐに返してしまうと、別の要求に割り当てられ、そこへ、遅れて届いた書き込みが入り込む。割り当てられた要求は、他の要求の KV キャッシュを読んで、おかしな出力を返す、または、他の利用者のデータが混ざる。エラーは出ない。
  • 影響を受ける条件：分離構成で、転送の途中で要求が中止され、領域が、書き込みの着地の前に再割り当てされること。3つの条件のどれか1つがなければ、起きない。長い文脈ほど、競合の窓が長い（短いプロンプトはミリ秒、100万トークン級は、秒から分）。
  • 影響を受ける版：SGLang の記事によると、既定の設定でも、分離構成が RDMA の転送とともに出た v0.4.x の系統（2025年の前半）から、v0.5.21（MORI は v0.5.22）まで。
  • 悪用の可能性：SGLang の記事は、クライアントが、長い文脈の要求を送り、途中で切断することで、競合の確率を意図的に上げられる、と書く。ただし、被害を受ける要求（犠牲者）や、書き込まれる場所は、選べない。内容が流れる向きは一方向で、中止した要求の KV キャッシュが、別の要求の KV キャッシュに入る。中止した側には、何も返らない。
  • 検出：運用者は、すでに露出があったかどうかを、確実には知れない（エラーもログも残らない）。任意で有効にできるチェックサムで、一部の遅れた書き込みを検出できる。
  • 遅延解放：中止された要求の領域を、すぐには返さず、プレフィルが書き込みを使い切ったという確認応答（ABORT_ACK）か、上限の時間まで保持する。v0.5.21 から、Mooncake と NIXL で、既定で有効。
  • 転送のバッチの上限：1回の転送の呼び出しの大きさに上限を設け、呼び出しがハングしても、残る書き込みを最小にする。
  • チェックサム（任意）：プレフィルが GPU で転送内容のチェックサム（Adler-32）を計算し、デコードが、要求を実行に入れる前に確かめる。既定では無効。有効にすると、転送ごとに GPU の読み取りと同期の分のコストがかかる。
  • 性能への影響：SGLang の測定（2×H100、1024 要求、7回ずつ）では、パッチの前後、機能の有無で、スループットは、統計的に区別できず、差は ±2% 以内だった。

運用者への推奨

  • Cloudflare の推奨（SGLang を分離構成で動かす運用者向け）：
    1. 各ノードで、エンジンの起動ログから、KV の領域の大きさと、文脈の長さを比べる（重みや量子化、並列化、メモリの割合を変えるたびに）。領域のほうが小さければ、文脈の長さを下げる。プロキシで制限を強制することや、エンジンが収まらないものを拒否すると仮定することはしない。
    2. v0.5.22 以降に更新して、領域の大きさに関わらず、長すぎる要求が、受け渡しの前に拒否されるようにする。
    3. 両方の役割で遅延解放を有効にし、転送のバッチを制限する。
    4. 破損の検出（チェックサム、カナリア）を、モデルが対応する範囲で有効にする。ただし、すべてのモデルの構造に対応しているわけではない（GLM-5.3 などへの拡張を作業中）。
    5. ロードバランサーが、不要な中止を作らないようにする。
  • SGLang の推奨：更新（v0.5.21 以降）、中止を両側に伝えるルーターの利用、更新後に遅延解放の指標で、保持が「使い切り」で解放されているかを確かめる。

今後の取り組み（Cloudflare の報告）

  • 構造で保証する：すべての物理ページに、再割り当てのたびに変わるタグを付け、各要求が期待するタグを記録し、デコードが読む前に対応を確かめる。読もうとしているページが、自分のものでなければ、その要求だけを失敗させる。夏に試作し、GLM-5.2 で試験して、スループットと末尾の遅延の悪化は1%未満だったが、信頼性の問題で、いったん無効にした。特定の注意の仕組みやモデルの構造に結び付いていたため、汎用の修正にするため、SGLang の開発元と、エンジンの本体に組み込む作業をしている。
  • 数学的に保証する：分散システムの整合性の不具合として、RDMA による KV キャッシュ転送の安全性を、形式手法（モデル化と証明）で確かめる作業に着手する。現実には、証明器で分からない部分も残ると見ている。

分かっていないこと

  • 個別の連絡：影響を受けた顧客への個別の連絡について、報告には書かれていない。
  • 漏れた内容：混ざった内容の種類や、どの顧客の情報が含まれたかは、公表されていない（155件は、応答の数）。
  • 研究者の報告：SGLang の記事は、発見と外部での検証を説明する研究者の報告を、近く公開すると書いている。この記事では、確認していない。
  • 悪用の有無の限界：「故意の悪用の証拠は見つからなかった」は、Cloudflare が、見つかった要求を調べた結果。ログに残らない形での悪用がなかったことの証明ではない（SGLang の記事も、運用者は、露出があったかを確実には知れないと書く）。

読むときの注意

  • 主な根拠は、Cloudflare 自身の報告と、推論エンジンの開発元の記事で、どちらも、事案の当事者（または当事者と連携した側）の説明。
  • 数字（155件、領域の大きさ、時刻）は、報告のまま。38分は、報告の時刻から筆者が計算した。
  • 「同じ種類の別の不具合」の節は、今回の事案の原因ではない。仕組みの理解のために並べている。
  • 影響を受けるバージョンや推奨は、2026年10月26日の公開時点のもの。
