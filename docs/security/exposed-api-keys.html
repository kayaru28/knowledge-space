公開のWebサイトに、使える状態の API キーが残っていた：1,000万サイトの調査「Keys on Doormats」

スタンフォード大学らが2026年に発表した論文「Keys on Doormats」から、1,000万の公開Webサイトで見つかった有効なAPIキー1,748件、見落とされる理由（ビルドで作られたバンドルの中）、露出が残る期間、通知の効果、勧められる対策を、棒グラフと表で整理する。

初回公開 2026-10-25 ／ 更新日 2026-10-25

ひとことで言うと

2026年の論文「Keys on Doormats」は、1,000万の公開 Web サイトを調べ、使える状態の API キー（外部のサービスを使うための認証情報）が、サイトの上にそのまま露出していたことを示しました。

14のサービス（クラウド、決済、メッセージなど）について、有効な認証情報1,748件が、9,804のサイト、5,693のドメインで見つかりました。露出した先には、世界の大手銀行、重要インフラの事業者、公共の安全に関わるシステムが含まれています。

露出の多くは JavaScript のファイルにあり、うち62%は、ビルドで作られたまとめ済みのファイル（バンドル）の中にだけあって、ソースコードの検査では見つかりません。露出は平均で12か月残り、研究者が通知すると、2週間で約半分が取り除かれました。調べたのは14のサービスだけなので、実際の露出は、これより多いと論文は述べています。

どう調べたか

  • 対象：HTTP Archive（Chrome の利用者が多く訪れる Web サイトを集めたデータをもとに、ページの読み込みを記録したもの）の、約1,000万の描画済みの Web サイト。ネットワークの要求や応答、JavaScript などが含まれます。
  • 検出：秘密の情報を探すツール（TruffleHog）で、認証情報らしい文字列（候補）を探します。
  • 確認：候補は、そのサービスの、利用者のデータを変えない窓口に問い合わせて、有効かどうかを確かめます。確認の方法は、事前に手作業で見直して、安全にしたとしています。
  • 結果：約200万の候補のうち、有効と確認できたのは1,748件（0.09%）でした。形が正しい候補の多くは、すでに取り消されたり、更新されたりしていました。

調べたのは、有効かどうかを確かめられる14のサービス（AWS、Azure、Alibaba、Bitly、Cloudflare、GitHub、Mailchimp、OpenAI、RazorPay、SendGrid、Slack、Stripe、Telegram、Twilio）です。調査の時点で有効だったものだけを数えるため、論文は、結果を実際の露出の下限としています。

何が見つかったか

  • 有効な認証情報1,748件が、9,804のサイト、5,693のドメインにありました。AWS の認証情報は、有効な露出全体の16%超で、4,693のサイトにありました。
  • 人気の高いサイトにもありました。Tranco の上位500のサイトにも、有効な認証情報が見つかっています。
  • 組織の種類は、世界の大手銀行（国際的に重要な銀行）、重要インフラの事業者、公共の安全に関わるシステム、医療機関に関わる事例などです（論文は、組織名を伏せています）。
  • 国別では、露出したドメインのうち、アメリカが20%（世界のドメイン全体では9%）、インドが16%（同5%）でした。

なぜ見落とされるのか

  • ソースコードの中には鍵がなく、ビルドの結果にだけ現れることがあります。そのため、ソースの検査（静的な解析）では見つからず、本番の Web サイトを動かして調べる検査（動的な解析）が必要になります。
  • 16%は、外部から読み込む、第三者の資源（外部のスクリプトなど）を通じて広がります。OpenAI の認証情報は、24%が外部の資源にありました。
  • 5%（478件）は、最初の HTML の応答に、そのまま含まれていました。

露出はどれくらい残り、通知で変わったか

HTTP Archive の9回分の記録で調べたところ、露出が残る期間は平均12か月で、サービスによって差がありました（Slack と Bitly は長く、AWS と Azure は短い）。研究者は、メールで運営者に通知し、取り除くこと（削除）と、無効にすること（取り消し）の両方を勧めました。

  • 削除だけでは足りません。削除しても、キャッシュや保存されたページに残り、取り消していない認証情報は取り出せます。削除は取り消しの約2倍の割合で行われ（50%と26%）、取り消しが後回しになっていました。
  • サービス別の平均では、47%が取り除かれました。OpenAI は、153件から44件に減りました（71%減）。
  • 6か月後には、取り消されていない露出は865件から660件に減り、取り消しが進んだとしています。一方、削除されていない露出は706件から1,019件に増えました。

論文が勧める対策

開発者：公開前に検査する

ビルドで作られたファイル（バンドル）も含めて、認証情報を検査し、見つかったらビルドを失敗させます。環境変数は、公開してよいものだけを明示して含め、認証情報らしいパターンは、コミットの前の検査で止めます。

開発者：鍵をクライアントに置かない

重要な API は、バックエンドを通して呼びます。本番ではない環境では、別のテスト用の認証情報を使います。

ツールの開発者：初期設定を安全側にする

設定を、クライアントに見せるものと見せないものに分け、宣言のないものは秘密とみなします。ビルドの段階で、バンドルから認証情報を検出します。

サービスの提供者：権限を絞る

権限を最小から始め、短い有効期間と自動の更新を勧めます。クライアント用の鍵は、権限が狭く、回数に制限があり、送信元に縛られ、バックエンドを止めずに取り消せるようにします。

筆者の整理：論文は、運営者が、公開用と思い込んだ認証情報を、安全だと扱っている例があるとしています。見えないのは、ソースではなく、ビルドの結果です。また、削除しただけでは直らず、取り消して初めて直ります。別のまとめ（国内の情報漏えい）では、JPCERT/CC が、アプリに秘密の鍵や、有効期間の長い認証情報を埋め込まないよう勧めています。この論文は、Web サイトの側で、同じ種類の問題が起きていることを示しています。
