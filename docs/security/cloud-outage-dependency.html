クラウドが止まると何が止まるか：ロンドンのゾーンの電源障害と、IDCFクラウドのランサムウェア被害

2026年10月の Google Cloud のロンドンのゾーンの電源障害と、IDCFクラウドのランサムウェア被害を、止まった範囲、時系列、取り出せたデータの数で比べ、ゾーンやリージョン、バックアップの備えが何に効いたかを公式の発表をもとに図で整理する。裁判所の mints の不調も扱う。10月27日に公表された、Google の詳細な分析（外部の停電と、発電機が起動しなかった制御の設定ミス）と、IDCフロンティアの調査結果（認証システムのオープンソースソフトウェアの脆弱性から侵入）も反映している。

初回公開 2026-10-22 ／ 更新日 2026-10-30

ひとことで言うと

2026年10月、クラウドが止まる出来事が続きました。ただし、止まり方はまったく違います。

10月20日の Google Cloud では、ロンドンのリージョンの中の1つのゾーンで電源の障害が起き、障害は6時間8分続き、そのゾーンの資源は約5時間半使えなくなりました（10月27日の詳細分析）。影響が出た製品は40にのぼります。一方、10月7日からの IDCFクラウドでは、ランサムウェア攻撃で東日本リージョン1の4つのゾーンが被害を受け、495の企業・自治体のデータが、取り出しや復元が困難な見通しとされました。侵入の原因は、認証システムが使っていたオープンソースソフトウェアの脆弱性だったと、10月27日に公表されています。

前者は設備の故障で、ゾーンを分けて置けば避けられる種類の障害です。後者は事業者の基盤への攻撃で、同じリージョンの複数のゾーンが一度に被害を受けました。どこに、どんな写しを持っておくかで、取り戻せるものが変わります。

リージョンとゾーン

クラウドの事業者は、サービスを地域ごとの「リージョン」に分け、リージョンの中をさらに設備が独立した「ゾーン」に分けています。Google の説明では、リージョンは3つ以上のゾーンから成り、3つ以上の物理的なデータセンターに置かれます。そして「ゾーンは、リージョンの中の1つの障害単位とみなすべき」としています。

Google は、高い可用性のために、アプリケーションをリージョン内の複数のゾーンに置くこと、リージョン全体を失う場合に備えて別のリージョンでも動かせるよう計画すること、データを別のリージョンに複製することを勧めています。

Google Cloud：ロンドンの1つのゾーンの電源障害

障害は日本時間の10月20日 15:08 に始まりました。最初の公表は約2時間半後で、そのときは原因も回避策も示されていません。原因が「電源の事象」と公表されたのは開始から約5時間後で、その時点で電源はすでに解消していました。

影響が出た製品は、公開中の更新では38でした。10月27日の詳細分析では40になっています。仮想マシン（Compute Engine）やディスク（Persistent Disk）、Kubernetes Engine のような土台のサービスに加えて、Cloud SQL、Spanner、BigQuery、Pub/Sub、Cloud Storage、ロードバランサ、VPC など、その上に作られたデータベースや分析、ネットワークのサービスにも及びました。

10月27日の詳細分析：原因と再発防止

Google は10月22日に暫定の報告を出し、10月27日に詳細な報告（Incident Report）を公開しました。時刻は太平洋時間で、日本時間への換算は筆者によるものです。

1. 外部の停電

電力会社から受けるフィードAが、施設の外の地中ケーブルの障害で停電しました。

2. 発電機が起動しなかった

発電設備は、自動で起動する信号を受け取れませんでした。UPS（無停電電源）の蓄電池が設計どおりに重要な負荷を支えましたが、残量が尽きて、データホールが全面停電しました。

3. 制御の設定ミス

発電機の起動を判断する制御装置（PLC）が、遮断されていたフィードBの上流側の電圧を検出するよう設定されていました。健全な電源があると誤認し、起動指令を出しませんでした。

筆者の整理：1つのゾーンの電源から、公開中の更新で38、詳細分析で40の製品に影響が出たのは、多くのサービスが同じ土台の上で動いているためです。Google 自身が勧めるとおり複数のゾーンに分けて置いていれば、避けられる種類の障害でした。ただし、リージョンの一部のサービスでもエラーの増加やネットワークの問題が出ています。また、回復のときは既存の処理が優先され、新しい処理はしばらく作れませんでした。障害が起きてから別の場所に移す、という方法は、そのとき使えるとは限りません。

IDCFクラウド：ランサムウェアによる被害

IDCFクラウドでは、10月7日の午前3時40分ごろに障害が起き、同じ日のうちにランサムウェア攻撃によるものと判明しました。IDCフロンティアは、二次被害やデータ漏えいを防ぐため、東日本リージョン1をネットワークから遮断し、システムを止めています。

第3報の時点では、被害を受けた4つのゾーンのデータは、取り出しや復元が困難な見通しとされ、復元できるのは利用者自身が持つバックアップからだけとされました。その後の第5報で、スナップショット機能を使っていた利用者については、バックアップデータを取り出せることが確認されています。

被害のなかったゾーンやリージョンにも影響は及びました。外部からアクセスできる管理コンソールが止まったため、仮想サーバーの起動や停止は、利用者の要望に応じて IDCフロンティアが代行しました。バックアップの機能も一時止まり、10月18日に安全を確認して再開しています。スナップショット機能は、まだ止まったままです。

10月27日の第7報：原因と再発防止

IDCフロンティアは10月27日の第7報で、一連の調査が完了したと報告しました。

  • 侵入の経路：IDCFクラウドポータルの認証システムに入り、管理コンソールを通じて、仮想化基盤の管理者権限を不正に取得しました。侵入の原因は、認証システムで使っていたオープンソースソフトウェアの脆弱性です。ソフトウェアの名前と、脆弱性の番号は書かれていません。
  • 10月7日の初動：6:20ごろに、サイバー攻撃の可能性を含めて調査を開始。6:48 に東日本リージョン1のポータルを停止し、7:00 に影響のあった4ゾーンのストレージ機器を切り離しました。9:00 に緊急対策本部を設置し、11:42 にランサムウェア攻撃と特定。12:15〜14:05 に他のリージョンのポータルを止め、全リージョンのポータルと外部をつなぐネットワークを遮断しました。16:00 から、外部のセキュリティ専門企業と調査しています。
  • 仮想サーバー内のデータ：外部への持ち出しを示す痕跡や裏付けは確認されていません。影響のなかったゾーンや他のリージョンでも同じです。情報の不正利用などの二次被害も、10月27日時点では確認されていません。
  • ポータルの登録情報：不正な照会は、第5報の48社から、最大71社に増えました。個人名や、個人名を含む可能性のあるメールアドレスなどが、最大31社分含まれます。外部への持ち出しの痕跡は確認されていません。最大4件で、ログインパスワードが不正に変更されており、リセットして、対象の顧客に個別に連絡しました。
  • バックアップ：取り出せると確認された顧客は、10月14日の194から、10月20日に206になりました。10月17日から取り出しと引き渡しを始めています。
  • 身代金：攻撃者との接触はなく、支払いも交渉もしていないとしています。
  • 被害の範囲：東日本リージョン1の4ゾーン（tesla、henry、pascal、joule）の495の企業・自治体です。IDCFクラウド TypeS と、IDCF プライベートクラウドは、対象外と書かれています。
IDCフロンティアが示した再発防止策（第7報より）
分野内容
体制外部の専門家を招き、社内のセキュリティ人材を集めた、独立した組織を設置（対応済み）

ポータルの再開は3段階です。第1段階（実施中）は、仮想サーバーの起動・停止、セキュリティ設定、ネットワーク設定、データベースの起動・停止・設定変更などの主要な操作を、同社が代行します。第2段階は、全機能の操作を同社が代行し、第3段階で、全機能を顧客自身が操作できる形で再開します。安全を確保するまで、提供は止まっています。

筆者の整理：ポータルの登録情報への不正な照会は、第5報の48社から、第7報の最大71社に広がりました。「仮想サーバー内のデータは外に出ていない」という調査と、「ポータルの登録情報が見られた」という調査は、対象が別です。前者の結果から、後者についても安全だったとは言えません。

裁判所の mints：1日ほど不安定な状態

民事裁判の書類をオンラインで出すシステム「mints」では、10月15日の午前9時ごろから、サインインできない、事件が表示されない、記録の一覧の画面が表示されないなど、不安定な状態が続きました。裁判所のお知らせでは、10月16日の午前9時の時点で同じ事象は確認されておらず、支障なく使える状態になったとしています。原因は書かれていません。

今回の2件で、どの備えが何に効いたかを並べます。何を、どこまで備えるかは、止まったときの影響の大きさと費用で決まります。この表は一般的な基準ではなく、今回起きたことの整理です。
