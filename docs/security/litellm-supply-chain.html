正規の配布経路から届いたマルウェア：LiteLLM 1.107.0 の乗っ取りと、崩された何重もの守り

2026年10月21日、AI の中継ソフトウェア LiteLLM の 1.107.0 が、PyPI と Docker の正規の配布先からマルウェア入りで配布された。公開されていた時間、確かめ方と対処、開発者の認証情報を使ってリリースの守りが崩された流れを、開発元の公式の発表から図で整理する。

初回公開 2026-10-22 ／ 更新日 2026-10-31

ひとことで言うと

AI のモデルを呼び出す中継のソフトウェア「LiteLLM」の 1.107.0 が、2026年10月21日、PyPI と Docker の正規の配布先から、認証情報を盗むマルウェア入りで配布されました。PyPI では約1時間45分（日本時間20時39分〜22時23分）、Docker Hub では約2時間半公開されていました。GitHub の正式なソースの 1.107.0 には悪いコードは入っておらず、攻撃者は名前のよく似たリポジトリから配布物を作らせました。

開発元は、3月の事件のあとリリースの手順を強めていました。しかし攻撃者は、3人の開発者の GitHub CLI の認証情報を手に入れ、そのうち組織の所有者の権限で保護を外して、リリースの仕組みそのものを書き換えました。開発元が10月23日に公開した正式な記録によると、起点は、5月27日に公開リポジトリへ誤って載った、社内の実験用の基盤（エージェント基盤）のマスターキーでした。この鍵は失効されないままで、攻撃者は10月10日にそれを使って組織の所有者の GitHub CLI のトークンを得て、CI を使ってさらに2人分を外部へ送らせました。10月21日の最初の投稿は、トークンが社内の LiteLLM のログから取られたと疑っていましたが、のちに訂正されました（10月27日追記）。

何が、いつ配布されたか

マルウェアは、認証情報を盗み、外部からのプログラムの実行を可能にする道具を読み込むものでした。1.107.0 より前のバージョンは安全で、法人向けの非公開の配布先も影響を受けていません。

影響を受けるのは、バージョンを固定せずに、11:39〜13:23 UTC の間に pip で入れた人と、11:46〜14:20 UTC の間に、上のタグの Docker イメージを使った人です。

確かめ方と対処

開発元は、1.107.0 で Python を起動した環境を、侵害されたものとして扱うよう求めています。仕込まれたファイル（cook.pth、sitecustomize.py など）が見つかれば侵害の証拠ですが、見つからなくても安全の証明にはなりません。

開発元が示す対処（10月21日時点の公式の発表より）
順番やること
1pip install から始めない。その環境で Python を起動すると、pip の実行も含めて、仕込まれたファイルがまた動く
2シェルから、仕込まれたファイルとそのキャッシュを消し、切り離されて動き続けるプロセスを止める
31.106.2 に固定して入れ直す。環境やイメージを一から作り直すほうがよい
4インターネットにつながるホストに入れたことがあれば、情報は持ち出されたと考える
5そのホストから届くものをすべて変える：クラウドの権限（IAM ロール）、LiteLLM のプロキシの DB に保存したすべての AI 事業者の鍵、マスターキーと仮想キー、DATABASE_URL のパスワード、ホスト上のプロセスの環境変数にあった秘密
6クラウドの記録で、インストールのころの権限の確認の呼び出しと、その後の外部からの権限の利用を調べる

何重もの守りは、どう崩されたか

開発元は、3月の事件のあと、リリースを非公開のリポジトリに移し、決まったワークフローと GitHub の信頼できる公開者（Trusted Publishers）の仕組みで公開するようにしていました。Docker のタグは書き換え不可にし、イメージに署名もしていました。公開できるのは、事務所に常に置かれた特定のノートパソコンに結びついたアカウントだけでした。

認証情報の出どころ（10月23日の正式な記録で訂正）

10月21日の最初の投稿は、トークンが「インターネットに公開されていた社内の LiteLLM のログから取られた」と疑っていました。開発元は10月23日に正式な記録を公開し、リクエストのログから、最初のトークンは別のサービスから出たと分かった、と訂正しています。

  • 5月27日：社内の実験用の基盤（エージェントを動かすための道具）のマスターキーが、設定ファイルとして公開リポジトリに誤ってコミットされました。気づいてコミットは上書きしましたが、鍵の失効は行われませんでした。
  • この基盤は、サービス用のアカウントではない、権限を絞っていない組織の所有者の GitHub CLI のトークンで動いていました。このトークンは二要素認証のあとのもので、重要な操作で求められる再認証の対象になりません。
  • 10月10日：攻撃者がマスターキーで基盤の API を呼び、設定の一覧から、所有者のトークンを得ました。続けて、一時的なブランチに、CI の秘密情報を外部の受け口へ送るワークフローを置いて動かし、記録を削除して、メンテナー2人分のトークンを得ました。10月12日にも、ほかの非公開のリポジトリで同様の操作が行われました（開発元は、毒入りの配布物に至る経路には使われていないとしています）。
  • 10月21日：保護に止められた変更を、所有者のトークンで保護を外して通し、2人目のトークンで本番の承認の関門を通り、3人目のトークンで実行の記録を削除しました。権限を一時的に広げていたことが、別々のトークンを使って、監査の記録を目立たなくすることに使われた、と開発元はみています。所有者のトークンがあれば、この制限自体も外せたはずだとも書いています。
  • 対応：開発元は、すべての内部システムとベンダーのトークンを失効させ、GitHub の組織から確認済みの1アカウント以外のメンバーを外し、すべての鍵が盗まれた前提で動いています。再発防止の取り組みは、翌週に共有するとしています。

最初の投稿にあった、Claude Code が GitHub CLI のトークンを応答に含めるという点は、正式な記録では扱われていません。

筆者の整理：利用者から見ると、マルウェアは正規の配布先から、正規の名前とバージョンで届きました。署名や信頼できる公開者の仕組みがあっても、その仕組みを動かす権限が取られれば、署名つきでマルウェアが出ます。守りは何重にもありましたが、それぞれを開ける人の認証情報が複数まとめて取られ、一時的に広げた権限も入口になりました。起点は、5か月前に公開リポジトリへ載った、失効されなかった鍵でした。一度でも公開された鍵は、公開された時点で漏れたものとして扱い、すぐに失効させる必要があります。実験用の基盤が、権限を絞っていない所有者のトークンで動いていたことも、被害を大きくしました。最初の説明が調査の途中のもので、のちに訂正されたことから、調査中の発表は、後で変わりうるものとして読む必要もあります。利用者の側では、バージョンを固定することと、新しいバージョンをすぐに入れないことが、被害の範囲を分けました。

関連する動き：Claude Code の VS Code 拡張が、Cursor のマーケットプレイスで侵害された（10月30〜31日）

LiteLLM の件と同じく、正規の配布の場所から届いた悪意のあるコードの事例です。発見した会社の報告で、公式の説明は確認できていません。

  • 発見と公表：セキュリティ会社の Phorion が、10月30日に公表し、10月31日に更新した。Cursor のマーケットプレイスで配布された「Claude Code for VS Code」の拡張（公式を名乗るもの）のバンドルに、攻撃者が遠隔から入れるようにする SSH のバックドアを置くコードが含まれていた。
  • 対象の版：初めの公表では 2.1.313 のみだったが、10月31日の更新で、Cursor の通知が、macOS と Windows 向けに配布された 2.1.312 と 2.1.313 を対象と特定したとして、書き直した。Cursor は、これらの版をマーケットプレイスから取り除いた。Cursor の通知そのものは、この記事では確認できておらず、Phorion の記述による。
  • 仕組み（概要）：拡張は、エディターを使う人の権限で動く。そのため、悪意のあるコードが、ローカルのファイル、ソースコード、開発の道具に、すぐに届く。注入されたコードは、拡張が読み込まれた時点で動き、利用者が拡張を操作する必要はない。攻撃者の鍵を登録し、外部のサーバーへ接続を張り、再起動後も残る仕組みを置く。macOS、Linux、Windows のそれぞれに対応するコードがある。
  • 目的と不具合（Phorion の評価）：長く使える、対話的なアクセスを得ることが目的。ただし、macOS の SSH を有効にする確認の手順に実装上の不備があり、標準の権限では SSH を有効にできず、受け入れ側の経路が成り立たない場合がある。この不備は影響を小さくするが、鍵の登録と居座りの仕組みは置かれるため、脅威は小さくないとしている。
  • 対処（Phorion の案内）：Claude Code for VS Code の 2.1.312 または 2.1.313 を使っていたかを確認し、使っていた場合は、インシデント対応を行う。
  • 分かっていないこと：配布物にコードが入った経路（開発元のアカウントや配布の仕組みのどこが破られたのか）、公開されていた期間、影響を受けた利用者の数、Anthropic や Cursor の公式の説明。
  • 筆者の整理：LiteLLM は、パッケージの配布（PyPI）の経路、今回は、エディターの拡張のマーケットプレイスの経路で、どちらも「正規の場所から届く」点が共通する。拡張は、エディターを使う人の権限で動くため、ソースコードや認証情報の置き場に近い。
