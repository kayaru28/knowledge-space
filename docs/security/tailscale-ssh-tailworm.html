Tailscale SSH の権限の欠陥：接続を許された後の権限の境界が破られた4件の勧告と、「ワーム」ではないという説明

2026年10月24日に外部の研究者が公開した報告「Tailworm」を受け、Tailscale が10月26日に出した4件のセキュリティ勧告と10月28日の調査ブログから、何が破られたか、誰が影響を受けるか、v1.104.4での修正、当面の軽減策、ワームではないという説明を整理する。

初回公開 2026-10-29 ／ 更新日 2026-10-29

ひとことで言うと

VPN サービス Tailscale の組み込み SSH サーバー（Tailscale SSH）などで、接続が認められたあとに、与えられた権限の範囲を超えた操作ができる欠陥が見つかりました。2026年10月26日に4件の勧告が出て、修正は v1.104.4 に入っています。

公式の説明では、これは「誰が接続できるか」を決める認証や方針の確認が破られたものではなく、接続が認められたあとの権限の境界の問題です。認証されていない攻撃者が任意のサーバーに入れるものではなく、「ワーム」でもない、と説明しています。

4件の勧告の内容

Serve の HTTP/2：権限情報の混ざり

同じ接続の複数の通信が状態を共有していたため、ある掲載先の権限情報（Tailscale-App-Capabilities）が別の掲載先に混ざることがあった。影響は、TLS つきの Serve で、権限の要件が違う掲載先を2つ以上持つ機器。

Serve の Unix ソケット先：root だけの入口に届く

TCP の転送が Unix ソケットを root として呼び出し、tailscaled のローカルAPIの入口にそのまま届いた。もう1つは、設定のあとでパスをシンボリックリンクに差し替えて確認をすり抜けられた。公式は、前者は機器の乗っ取りにつながりうると説明している。対象は、設定を書ける操作者がいる、または掲載先のパスに書き込める利用者がいる機器。

SSH のセッション：メモリが増え続ける

認証されたピアが、画面サイズの変更や環境変数の追加を続けると、tailscaled のメモリが増え続け、切断後も戻らなかった。メモリ不足で tailscaled が落ちると、その機器の Tailscale の接続がすべて止まる。方針で許された SSH のセッションが必要。

SSH の Unix ソケット転送：root だけのソケットに届く

root で動く SSH サーバーが、パスの文字列だけを確認して、操作は root として行っていた。転送（ローカル・リモート）で、Docker のソケットや tailscaled のローカルAPIといった root だけのソケットに届く。対象は、SSH が有効で、方針で転送を許している機器。

公式の説明の要点

  • どこが問題か：「接続が認められたあとの権限の強制」。認証やアクセス方針の確認ではない。
  • 攻撃の前提：tailnet の中の認可された端末をすでに押さえていること、方針ファイルで SSH が明示的に許されていること、そして欠陥を使える条件。
  • 「ワーム」か：自己増殖して勝手に広がるものではなく、方針ファイルが許す接続の範囲での、横の移動にあたる、と説明している。到達できるのは、方針がすでに SSH を許していた機器だけ。
  • 報告にあった Serve と Funnel の5件：3件はバグで、v1.104.4 で修正。2件は設計どおりの動き（Funnel の属性の確認を回避するには機器の管理者権限が要る／TS_SERVE_ALLOW_ALL_INTERFACES は tailnet の外へ出すための任意の設定）。
  • Conn25：報告にあった欠陥は、まだ公開前の次世代のアプリコネクタのもの。以前から把握しており、公開していない理由の1つ。いま使える安定版のアプリコネクタは影響を受けない。

利用者がやること

  • v1.104.4 以降に更新する。公式は、Tailscale SSH を使う利用者に勧めている。
  • すぐ更新できないときの軽減策：tailscaled の環境変数に TS_SSH_DISABLE_FORWARDING=1 を設定して再起動する。SSH 全体を止めずに、転送だけを止められる。
  • SSH の方針を見直し、必要なユーザーと端末だけに絞る。機密性の高い機器には、追加の認証を求める「チェックモード」を検討する。
  • 10月26日の時点で公式は、「全員が Tailscale SSH を止めることは勧めない」と説明していた。

読むときの注意

  • 公式の説明をもとにしている：外部の研究者の報告そのものは読んでおらず、その内容と公式の説明が一致するかは確認していない。
  • 悪用の有無：公式の資料には、実際に悪用されたかどうかは書かれていない。
  • 影響は設定しだい：勧告ごとに対象が違い、SSH の転送を許していない、Serve を使っていない、といった環境では、当てはまらない勧告がある。

見方（筆者の整理）

  • 「認証」と「接続後の権限」は別の層で、後者の境界が root で動くサーバーの内側にあると、設定の文字列の確認だけでは守りきれない、という例。修正の説明にも、転送を root ではなく認証された利用者として行うよう変えた、とある。
  • Tailscale は、報告を受けた時点で関連する問題の調査と修正がすでに進んでいた、と説明している。公開の2時間前に報告を受けた、という経過と合わせて、情報の出る順序が対応を急がせた例でもある。
  • 過去の勧告にも、Tailscale SSH の問題は複数出ている（7月の勧告では、環境変数がコマンドラインに見える問題、同じ月の別の勧告では、-i というユーザー名で root のセッションを得られる問題）。設定の見直しは、一度きりの対応ではなく継続的なものとして扱うのがよい。

用語メモ

tailnet
Tailscale でつないだ、自分たち専用のネットワーク。
方針ファイル（ACL）
誰がどの機器に、どのユーザーとして接続できるかを決める設定。
権限昇格
許されている範囲より大きな権限を得ること。
SSH の転送
SSH の接続を使って、別のポートや Unix ソケットへの通信を中継する機能。
Unix ソケット
同じ機器の中のプログラム同士が通信する入口。Docker の操作用の入口などがある。
Serve / Funnel
手元のサービスを tailnet に載せる機能（Serve）と、インターネットにも公開する機能（Funnel）。
