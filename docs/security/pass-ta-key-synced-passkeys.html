Googleの同期パスキーを狙う3つの攻撃「Pass-ta-key」：暗号は破られていないが、端末がマルウェアに侵されると本人確認の前提が崩れる

Palo Alto Networks の Unit 42 が2026年8月3日に公表した研究から、Chrome（Windows）と Google のクラウド認証機構を使う同期パスキーに対する3つの攻撃（Pass-ta-key、Silver、Golden）の仕組み、成立する条件、確認された事業者の不備、Google の対応、提案された対策を整理する。

初回公開 2026-10-29 ／ 更新日 2026-10-29

ひとことで言うと

Palo Alto Networks の研究部門 Unit 42 は2026年8月3日、Google の同期パスキーを狙う3つの攻撃（Pass-ta-key、Silver、Golden）を公表しました。いずれも、利用者の Windows 端末にマルウェアがすでに入っていることが前提です。

パスキーの暗号を破るものではなく、端末の登録・復旧・信頼確認の仕組みを悪用して、利用者の操作なしに認証を成立させたり、同期パスキーを守る鍵を取り出したりします。パスキー自体の価値を否定する研究ではない、と原文も述べています。

3種類

公表された攻撃（Pass-ta-key／Silver／Golden）

32バイト

同期パスキーをまとめて守るマスター鍵（SDS）の大きさ

1ビット

利用者検証の有無を示す UV フラグ。事業者の検証の甘さが突かれた

対象と前提

  • 対象：Windows の Chrome に入った Google Password Manager、TPM のある端末。Google のクラウド認証機構（Cloud Authenticator）を使う方式です。
  • 前提：マルウェアが端末にすでにあります。昇格した権限は要らず、通常のユーザー権限で足ります。
  • iOS と Android の Google Password Manager は、クラウド認証機構を使わず、別の仕組みだと原文は説明しています。
  • Unit 42 は、責任ある開示をしたと述べています。

3つの攻撃

Pass-ta-key：端末のなりすまし

Chrome が TPM に結びつけて保存している端末識別鍵を、マルウェアが取り出し、Windows の標準の暗号 API で署名に使います。クラウド認証機構には「信頼できる端末からの要求」に見え、正当な認証結果が返ります。利用者の同意、端末のロック解除、生体認証なしでログインできます。

Silver Pass-ta-key：本人確認の鍵のすり替え

端末の登録を無効にして、Chrome に再登録させます。再登録では、利用者検証の鍵が2回目の利用まで作られない「保留」の状態があり、その間に攻撃者が自分の公開鍵を登録します。クラウド認証機構は、新しい鍵が安全なハードウェアで作られたかを検証しません。以降は、被害端末が手元になくても、利用者検証つきの認証を作れます。

Golden Pass-ta-key：マスター鍵の取得

同期パスキーを暗号化するマスター鍵（SDS）を狙います。端末の登録のときにクライアントへ渡され、研究では、Chrome の画面のログに平文で出ていました。Google は報告後にログへの出力を取り除きましたが、SDS はなお Chrome のメモリに平文で存在しました。取り出して同期データを復号すると、パスキーの秘密鍵を復元できます。

「UV フラグ」1ビットの扱い

  • 認証結果の中の UV フラグが、利用者検証（生体認証や PIN）をしたかどうかを示します。
  • 事業者（ログインを受け付けるサイト）が利用者検証を必須にして、フラグを検証すれば、Pass-ta-key は通常失敗します。GitHub のパスキー認証では失敗しました。
  • ただし、利用者検証を「必須」にしていても、フラグを十分に検証せず認証を受け入れる事業者が見つかりました。その場合は端末識別鍵だけでアカウントを乗っ取れます。原文の例は eBay で、報告のあとに修正し、いまはフラグを検証しています。ほかの事業者にも報告したと述べています。
  • Silver は UV フラグがついた認証を作れるため、事業者がフラグを検証していても突破できます。

影響の違い

原文の説明より
攻撃攻撃に必要なもの回復
Pass-ta-key認証のたびに、被害端末上のマルウェア原文に個別の記載なし（事業者がフラグを検証すれば通常は失敗する）
Silver鍵のすり替えのあとは、被害端末が手元になくてもよい端末の登録解除や再登録で止められる
GoldenSDS を一度取り出せば、将来のパスキーも復号できる現状の実装では SDS の更新・失効の仕組みがなく、回復が限られる

提案された対策

  • 事業者：userVerification を required にするだけでなく、UV フラグをすべての認証結果で検証する。
  • 認証情報の管理側：新しく登録される端末の鍵のアテステーションを検証する。再登録と復旧の流れを強化し、状態ファイルの削除後の再登録の繰り返しを検知・制限する。
  • 鍵の扱い：マスター鍵をクライアントに渡さない（ログやメモリに出さない）。暗号の処理を隔離環境の中で完結させる。パスキー関連のローカルデータへのアクセスを、ブラウザのプロセスに限る。
  • 異常の検知：署名カウンタは、同期パスキーでは一定の値のことが多く、不正利用の手がかりになりにくい。Google は、同期の仕組みで全体で一貫したカウンタは作りにくいと述べています。
  • 日常の使い方での手がかり：通常のパスキーの利用では出ない、回復用 PIN の要求が繰り返されたら、登録の流れが再実行された可能性がある、と原文は述べています。

読むときの注意

  • 2026年8月3日の時点の研究です。その後の Google の対応は確認していません。原文が書く Google の対応は、SDS のログ出力を取り除いたところまでです。
  • 対象は Windows の Chrome と Google Password Manager に限られます。他のパスキーの提供者に同じ攻撃が当てはまるかは、この研究の範囲外です。
  • 前提は端末の侵害です。マルウェアが端末にない状態で、これらの攻撃が成立するとは書かれていません。

見方（筆者の整理）

  • 原文の結論は、パスキーはパスワード由来の攻撃を大きく減らす一方、端末の侵害は脅威の想定から外せない、という整理です。端末が出す「信頼できる端末」の合図を、侵害された端末が操作できる、という点がこの研究の核心です。
  • 事業者側のフラグの検証の甘さは、設定で必須にしているだけでは足りない、という実装の例です。
