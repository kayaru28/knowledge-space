証明書の信頼はどう守られているか：eMudhra の中間認証局の鍵の侵害と、各社の4日間の対応

2026年10月17日に報告された eMudhra の中間認証局8つの秘密鍵の侵害について、信頼の鎖のどこが破られたか、Chrome・Mozilla・Go・認証局の対応の時系列、遮断が届く3つの道筋を、公式の記録をもとに図で整理する。Let's Encrypt のドメイン確認の強化も扱う。

初回公開 2026-10-22 ／ 更新日 2026-10-31

ひとことで言うと

2026年10月17日、インドの認証局 eMudhra の中間認証局の証明書8つについて、秘密鍵が誰でも割り出せる状態だったことが報告されました。Mozilla は、報告者の方法を知らないまま、自分たちでも鍵を割り出せたことを確認しています。原因は鍵の作り方の欠陥で、秘密鍵の値が極端に小さかったためです。

この鍵があれば、どのドメイン名の証明書でも作れてしまいます。Chrome と Mozilla は報告の当日に、配信型の遮断リストでこれらを遮断しました。そのあと鍵を割り出す人が次々に現れたため、10月20日、Mozilla と Chrome は上位のルート証明書そのものの信頼を外す方針を決めました。Go も10月19日のセキュリティリリースで、8つの公開鍵を含む証明書チェーンを検証の結果から除外しています。

10月22日、eMudhra は世界向けの SSL/TLS 証明書の事業から撤退すると発表しました。

証明書の信頼のしくみと、破られた場所

ブラウザや OS は、信頼する「ルート証明書」の一覧を持っています。ルートは中間認証局に署名し、中間認証局が Web サイトの証明書を発行します。中間認証局の秘密鍵を持っていれば、ルートまでつながった「正しく見える」証明書を、どのドメイン名に対しても作れます。

4日間の対応

Mozilla の Bugzilla、dev-security-policy の議論、Go のリリース履歴とコミットより
組織対応
Chrome10/17 に CRLSet で TLS 用6つを遮断。コード署名用の2つは、Chrome が TLS で使わせないため遮断は不要。Chrome Root Store v43 で上位のルートを外す
Mozilla10/17 に OneCRL で遮断。10/20 にルート emSign ECC Root CA - G3 の信頼を緊急に外す。NSS の更新と、Firefox の臨時の版
eMudhra10/18 に8つを失効。10/20 に G3 の下での発行を停止。約3万件（97% が ACME 経由）を、RSA のルート G1 の下の中間認証局へ移す
Sectigo10/19 にクロス署名した証明書を失効
Go10/19 の Go 1.27.3 と 1.26.10。8つの公開鍵（SPKI）のハッシュを持つ証明書を含むチェーンを、検証の結果から除外する。macOS や Windows の OS の検証を使う場合にも適用
Apple・Microsoft報告を受けた（Bugzilla の記録）。それぞれの対応内容は、公式の発表を確認できていない

Go の Issue とコミットは、対象を「特定の認証局」としか書いておらず、eMudhra の名前を出していません。時期と件数（8つ）は今回の件と一致します。

原因：鍵の作り方の欠陥

  • 8つの鍵は、2025年4月30日の鍵生成の儀式（キーセレモニー）で作られた24の中間認証局の一部です。24は、3つの系列（A、B、C）×2つの方式（RSA4096、P-384）×4つの用途（DV、OV、EV、コード署名）でした。
  • 影響を受けたのは、B 系列と C 系列の P-384 の鍵すべてです。
  • Mozilla の分析では、P-384 の秘密鍵は本来、非常に大きな範囲から無作為に選ぶ整数です。8つの鍵は、どれも256未満の整数で、ほぼ一瞬で割り出せました。A 系列と、その置き換えの A-1 系列の P-384 の鍵は、より多くの手間をかけても割り出せなかったとしています。
  • eMudhra は、鍵はハードウェア（Utimaco の HSM）で生成したと説明しています。鍵の生成を起動したスクリプトを詳しく調べているとしています。ほかの発行用の認証局は別のメーカーの HSM で作っていて、同じ問題はないとしています。
  • eMudhra によると、G3B と G3C は欧州と米国の業務用に作ったもので、本番で使っていたのは1つだけでした。Web サイトなどの証明書は発行しておらず、コード署名用の2つも証明書を発行していません。

Mozilla は、2025年の別の件（同じ6つの中間認証局の CRL の署名が正しくなかった件）との関係も指摘しています。悪用されたかどうかは、確認した資料には書かれていません。鍵を割り出す方法の詳細は、このページでは扱いません。

遮断が届く3つの道筋

Mozilla は、多くの機器やソフトには失効情報を受け取る有効な仕組みがないことを懸念しています。ルートの信頼を外したのは、失効情報を使わない利用者や、特定の中間認証局だけを外す仕組みのない利用者を守るためだと説明しています。

関連する動き：Let's Encrypt が、ドメインを確かめる拠点を増やす

Let's Encrypt は10月15日、証明書を出す前にドメインを持っていることを確かめる拠点を増やすと告知しました。本拠地のデータセンターに加えて、ネットワーク上の別の場所（リモートパースペクティブ）からも確かめる仕組みで、その数を4か所から6か所にします。

  • 予定：ステージング環境で10月27日、本番環境で11月10日。業界の基準（Baseline Requirements 3.2.2.9）への準拠期限は12月15日です。
  • 基準は、リモートパースペクティブが、少なくとも2つの異なる地域インターネットレジストリ（RIR）の地域にまたがることを求めています。
  • Let's Encrypt は、利用者への影響はほとんどないと見込んでいます。

eMudhra の件は「認証局の鍵そのもの」の問題で、Let's Encrypt の件は「証明書を出す前の確認」の強化です。どちらも、信頼の鎖のどこか1か所が破られたときに、被害を小さくするための仕組みです（筆者の整理）。

その後の動き：eMudhra は世界向けの TLS 証明書から撤退

10月21〜22日の動き（NVD、mitmproxy の変更履歴、eMudhra の発表より）
日付動き
10月21日Go のセキュリティチームが、Go の修正（信頼できなくなった中間証明書を検証で拒否する一覧）を CVE-2026-111943 として登録
10月21日通信を途中で見るための道具 mitmproxy の開発中の版に、漏れた中間認証局の鍵で TLS 証明書に署名する設定が加わった。鍵が出回っていて、遮断が届かない環境では、なりすましの証明書が信頼されうることを示す
10月22日eMudhra の取締役会が、世界向けの SSL/TLS 証明書の事業から自ら撤退すると決定

eMudhra は、この事業は売上の約1%で、コストの増加や無料で証明書を出す事業者の存在で採算が下がっていたうえ、SNS での拡散で事業の規模に見合わない注目を集めたと説明しています。問題の中間認証局は発見から14時間以内に失効し、そこから発行された利用者向けの証明書はなく、設備への侵入や情報の漏えいもないとしています（いずれも同社の説明）。

移行の間は、RSA のルート（G1）を使い続け、利用者には提携先の証明書への無料の差し替えを案内します。失効と状態の確認のサービスは、発行済みの証明書がすべて期限切れか差し替えになるまで続け、ブラウザの側への原因の最終報告などの約束も果たすとしています。インド国内を含む電子署名の証明書やサービスは、影響を受けないとしています。

10月31日の追記：Apple が同梱する開発ツールについての指摘（10月28日）

  • コミュニティが運営するサイトの指摘（10月28日）：Apple は10月17日にこの件の報告を受けたが、10月28日の時点で、macOS に同梱の開発者向けツール（git、curl、python3 など）は、侵害された eMudhra の証明書をまだ信頼している。10月26日に公開された macOS 27.2 でも直らず、利用者が手で行った回避策が元に戻って、再び脆弱になった、としている。ほかの多くのプロジェクト（ボランティアが運営するものを含む）は、数日前に修正を出した。
  • 影響の見立て（同サイト）：ネットワークの途中にいる人が、これらのツールの HTTPS の通信を横取りできる。git では、HTTPS 接続での取得や更新で、攻撃者が選んだコードが届いたり、送った内容が途中で書き換えられたり、GitHub のトークンなどの認証情報が横取りされたりしうる。Safari など、Apple のネットワーキングの枠組みを使うアプリは、すでに保護されているとしている。
  • 手元の確認（同サイトの案内）：同サイトが用意した確認用のサーバーに git や curl でつなぎ、証明書のエラーが出れば保護されていて、通れば影響がある。確認用のサーバーは第三者のもので、認証情報を渡さないよう、案内どおりの形で使う必要がある。
  • 当面の対処（同サイト）：影響を受けるルートを手で外す手順がある。ただし、Apple の案内によると、macOS の更新で元に戻りうるため、更新のたびに確認と対処をやり直す。macOS のマシンを CI などのビルド環境に使っている場合は、サプライチェーンのリスクとして評価する。
  • 公式の発表：Apple の公式の発表は、確認できていない。上の内容は、同サイトの指摘で、Apple の対応や macOS 27.2 の内容は、この記事では確かめていない。

利用者が確かめること

macOS の開発ツール（git、curl、python3）

コミュニティの指摘では、10月28日の時点で未対応です。確認用のサーバーで確かめ、必要なら手でルートを外します（上の追記）。

Go で作ったプログラム

Go 1.27.3 または 1.26.10 以降でビルドし直します。Go は、OS の検証を使う場合にも、8つの公開鍵を含むチェーンを除外します。

ブラウザ

最新版に更新します。Android 版 Firefox は、一部で遮断リストが起動時に読み込まれない問題があり、158.0.2 で修正されました。

ルートの一覧を同梱するライブラリ

certifi などを更新します。失効情報を確かめない環境では、ここが更新されるまで守られません。

eMudhra の証明書を使う Web サイト

ECC のルート G3 の下の証明書は、別の経路に移す必要があります。eMudhra は世界向けの TLS 証明書から撤退するため、案内に従って、提携先の証明書への差し替え（無料）を進めます。移行の間は RSA のルート G1 が使われます。

このカードは、各社の対応からの筆者の整理です。

用語メモ

認証局（CA）
Web サイトなどの身元を確かめ、証明書を発行する組織。
ルート証明書
ブラウザや OS が最初から信頼している、認証局の大元の証明書。
中間認証局
ルートから署名を受け、実際に証明書を発行する認証局。
秘密鍵
証明書に署名するための鍵。漏れると、なりすましの証明書を作られる。
失効
期限の前に、証明書を無効にすること。
CRLSet・OneCRL
Chrome と Firefox が配信する、遮断する証明書の一覧。
クロス署名
別の認証局のルートからも署名を受けて、信頼される経路を増やすこと。
CT（Certificate Transparency）ログ
発行された証明書を、誰でも確かめられるように記録する公開の台帳。
HSM
鍵を安全に生成・保管するための専用の装置。
BGP ハイジャック
インターネットの経路情報を偽り、通信を横取りする攻撃。
