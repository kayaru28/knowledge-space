AI が書いた証明で、100以上のオープンソースのライブラリを形式検証：「テストを証明に変える」方法と、その限界

Anthropic が2026年10月22日に公表した、AI（Claude）に機械語（RISC-V）の上の証明を書かせて、123のライブラリを検証した取り組みについて、しくみ、結果、見つかったバグの例、費用、限界を、公表された記事の原本から整理する。

初回公開 2026-10-27 ／ 更新日 2026-10-27

ひとことで言うと

Anthropic は2026年10月22日、AI（Claude）にプログラムの正しさの証明を書かせて、100以上のオープンソースのライブラリを形式検証した、と公表しました。形式検証は、コードが決めた規則を必ず守ることを数学的に証明する方法で、これまでは専門家が何年もかける作業でした。

今回の対象は、コンパイル後の機械語（RISC-V）です。123のライブラリの239か所の入口について、64MB未満のどんな入力でも異常終了しないことを、証明検査器で確かめたとしています。一方で、「検証した」ことは「バグがない」ことではなく、成り立つ前提もはっきり書かれています。

何をしたのか

  • 背景：Anthropic は、十分に試験されたソフトウェアにもバグは残り、AI がそれを見つけて悪用する力も上がっている、と述べている。例として、Linux カーネルで最近1,000件を超える脆弱性が公開されたことを挙げている。
  • 目的：バグを探して直すだけでなく、「規則を破るバグはもうない」ことを証明する。これが形式検証で、これまでは専門的な技能と長い時間が必要だった（例：seL4 というカーネルは、作るのに2人年、検証に20人年かかった、と同社は紹介している）。
  • 共同：Theorem という会社と共同で行った。機械語（RISC-V）と Linux のプロセスの動きを数学で書いた「意味づけ（セマンティクス）」は Theorem のもの。
  • 成果の公開：証明の一部と、RISC-V と OS の意味づけを公開して、誰でも検証・再利用できるようにする。Theorem は、同じ手順を他のオープンソースにも実行する提案と、始めるための Claude 用のスキルの公開をしている。

しくみ：テストを証明に変える

  • 証明するには、「正しい」とは何かを決める仕様が要る。多くのプログラムでは、これが難しい。そこで、すでにあるテストを仕様に変えた。
  • 使ったテスト：ファジング。開発者が書いた「入口（エントリポイント）」に、膨大な量の半ランダムな入力を流して、異常終了する入力を探す。力任せの方法で、すべての経路を試せる保証はない。
  • 変換：ライブラリと既存のファジングのテストを RISC-V の実行ファイルにコンパイルし、「64MB未満のどの入力でも異常終了しない」という仕様を、機械語の上で作る。証明できれば、その入口をファジングしても、もうバグは見つからない。
  • 分担：Claude が証明を書き、Rocq という証明検査器が、仕様を満たすかを機械的に確かめる。人が証明を一行ずつ読む必要は、ほとんどない。
  • 対象：Google の OSS-Fuzz。C と C++ のプログラムには、メモリの不正な操作を検出する AddressSanitizer（ASan）が入り、不正な操作があると異常終了する。つまり、メモリの安全性（脆弱性の主な原因）が仕様に含まれる。
  • バグが見つかったとき：Claude がコードを直し、仕様を作り直して、もう一度証明する。証明を簡単にするためだけにプログラムを書き換える（報酬ハッキング）のを防ぐため、修正には減点を付け、修正で変わる入力が何で、どれだけ少ないかを証明すれば加点した。修正は記録して、報酬ハッキングの兆候がないかを監査した、と説明している。

結果

証明した範囲

数週間で、123のライブラリの239か所の入口について、64MB未満のどんな入力でも異常終了しないことを証明した。機械語の中央値は約1万8,000命令。

証明の量

証明は約1.8億行の Rocq。1件の証明は約60万行が目安。同社は、この量でも、信頼する必要があるのは、意味づけ、証明した主張の文面、証明検査器の3つだけだと説明している。

見つかったバグ

証明を試みる過程で、数百のバグが見つかった、と同社は述べている。ファジングでは見つかりにくいものも含む（下の「見つかったバグの例」）。

効率

小さな36課題で、Opus 5.5 は、半数を Opus 5 より約40%少ないトークンで証明した。複数のエージェントが証明を共有すると、トークンは17%減った。

見つかったバグの例

  • あるライブラリが持つ、展開（解凍）処理の自前のコピーで、カウンタの桁あふれ（アンダーフロー）から範囲外への書き込みが起きる。約20MBの入力で、まれな並びのときだけ起きる。
  • 画像のデコーダで、範囲外の読み出し。64MBの入力と2GB超のメモリが必要。
  • 別のライブラリで、同じファイルへの2つのハンドルに対して、特定の順番で呼び出したときの範囲外の読み出し。
  • libexpat の CVE-2026-56132 を再発見した。深く入れ子になった入力が必要。
  • クラッシュしない論理的なバグ。メモリの安全性を証明する途中で、アプリが読み込めるファイルを制限する機能が、いつも効くわけではないことに気づいた。
  • 同社は、ファジングは入力が小さく（多くは1MB以下）、コードの網羅率を手がかりに探すため、こうしたバグは見つかりにくい、と説明している。

費用と今後

  • 費用：証明には、数億トークンが必要になることがある。同社は、これを大きな障壁と認めている。
  • 新しいモデルほど少ない：36課題の比較で、Opus 5.5 は、Opus 5 より約40%少ないトークンで半数を証明した。同社は、この傾向が続くと見ている。
  • 証明は再利用できる：エージェントが互いの証明を写せるようにすると、トークンは17%減り、単独では失敗した課題に成功した例もあった。今回の大規模な作業でも、C ランタイムの初期化や ASan など、どのプログラムにも共通する部分が多く、別のチームの完成した証明を写して、自分のプログラムに合わせて直す形になった。
  • Theorem は、Nix という仕組みの全体を検証する計画を公開している。対象には、glibc、OpenSSL、cURL といった重要な基盤が含まれる。

限界と読むときの注意

  • 「形式検証済み」は「バグなし」ではない。証明検査器が確かめるのは、仕様を満たすことまでで、仕様が現実に合っているかは確かめられない。CPU や OS の意味づけが現実と違えば、検証済みでもバグは起きうる。
  • 現実の機械との差：証明は、単一スレッドで静的リンクの RISC-V の実行ファイル（musl という C ライブラリ）についてのもの。多くの人は x86 や ARM で、glibc に動的にリンクして使う。
  • 主張の範囲：異常終了しないこと（ASan の検出を含む）を証明したもので、ASan はすべてのメモリの不具合を検出するわけではない。すべての入口を検証したわけではなく、入口をすべて検証しても、ライブラリ全体（使われないコードなど）が対象になるとは限らない。呼び出す側の誤用で、メモリが壊れることもある。
  • 信頼の対象：Rocq、RISC-V と Linux の意味づけ、証明した文面は、信頼する必要がある。同社は、これを堅くするのは、すべてのコードをデバッグするより扱いやすい、としている。
  • 出どころ：Anthropic 自身が、自社のモデル（Claude）について公表した内容。数字は同社が示したもので、ここでは再現していない。同社は、独立した検証を歓迎するとして、証明の一部を公開している。

見方（筆者の整理）

  • 形式検証の主な壁は、証明を書く人手だった。この記事は、その壁を AI が下げうることを、大規模な事例で示した、という位置づけになる。
  • ただし、検証の価値は、前提の置き方で変わる。今回は、実際の利用環境（x86、ARM、動的リンク、複数スレッド）より狭い前提での証明で、同社自身もその差を限界として挙げている。
  • 見つかったバグの多くは、証明の途中で見つかった。証明が完成しなくても、証明を試みること自体がバグ探しになる、と同社は述べている。
形式検証
プログラムを数学的な模型にして、決めた規則を必ず守ることを証明する方法。
ファジング
プログラムの入口に、大量の半ランダムな入力を流して、異常終了する入力を探すテスト。
エントリポイント（入口）
開発者がテストのために用意した、プログラムの入り口。ここで異常終了する入力は、作者が気にするバグ。
Rocq

RISC-V
